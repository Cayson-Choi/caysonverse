# caysonverse 기획문서 (설계 스펙)

- 작성일: 2026-07-14
- 상태: 1차 버전(v1) 확정 — 구현 착수 기준 문서
- 작성 경위: 발주자(AI 강사)와의 브레인스토밍 대화로 요구사항을 확정하고, 기술 검증 리서치(라이브러리 버전·네트워크 설계·에셋 라이선스)를 거쳐 작성함

## 1. 프로젝트 개요

**caysonverse**는 웹 브라우저에서 링크 클릭만으로 접속하는 3D 메타버스다. 접속자는 닉네임과 캐릭터를 고르고 3D 공간에 입장해, 다른 접속자들과 함께 돌아다니고 머리 위 말풍선으로 대화한다.

- **운영자**: AI 강사 (1인 운영)
- **용도**: ① 강의/수업 공간 ② 수강생·커뮤니티 상시 라운지
- **핵심 가치**: 설치·가입 없는 즉시 입장, 실시간 현장감(아바타+말풍선), 강의 도구(공지·강퇴, 향후 화면공유)

### 1.1 v1 범위 (이번에 만드는 것)

| 기능 | 내용 |
|---|---|
| 게스트 입장 | 닉네임(2~5자) + 프리셋 캐릭터 4종 + 색상 선택 → 즉시 입장. 회원가입/DB 없음 (⚠️ 36장: 지금은 캐릭터 조립실 — 부품·색·목소리를 골라 조립) |
| 3D 월드 | 하나의 맵에 라운지 + 강의실 두 구역, 걸어서 이동 |
| 실시간 동기화 | 최대 100명 동접, 아바타 위치·방향 실시간 표시 |
| 말풍선 채팅 | 채팅 시 머리 위 말풍선 6초 + 접이식 채팅 로그 |
| 이모지 리액션 | 👍 ❤️ 😂 👏 🎉 🙋 6종, 머리 위 3초 표시 |
| 강사용 관리 | 관리자 코드 입력 → 전체 공지 배너, 사용자 강퇴 |
| 모바일 | 가상 조이스틱 + 터치 카메라, 저사양 자동 최적화 |
| 재접속 | 순단 시 20초 내 자동 복귀 (같은 위치·캐릭터) |

### 1.2 v2 이후로 미루는 것

- 화면 공유/발표 (WebRTC) — 강의실 스크린 오브젝트는 v1에 미리 배치
- 음성 대화
- 계정/영속 저장(DB), 지속 밴
- 룸 분할·수평 확장 (100명 초과)

## 2. 사용자 시나리오

### 2.1 수강생 (게스트)
1. 강사가 공유한 링크 클릭 → 입장 화면
2. 닉네임 입력, 캐릭터 4종 중 선택, 색상(파스텔 팔레트) 선택 → [입장하기] (⚠️ 36장: 지금은 캐릭터 조립실에서 부품·색·목소리를 고른다)
3. 라운지 스폰 지점에 등장. PC는 WASD/방향키 + 마우스 드래그 카메라, 모바일은 왼쪽 아래 다이내믹 조이스틱 + 오른쪽 터치 드래그 (조작은 2026-10-31 개편으로 35장 기준)
4. Enter(또는 채팅 버튼)로 채팅 → 내 머리 위 말풍선 + 로그 기록
5. 이모지 버튼으로 리액션
6. 강의 시간엔 강의실 구역으로 걸어가 착석 지점 근처에서 수업 참여

### 2.2 강사 (관리자)
1. 입장 화면에서 닉네임 등 입력 + [관리자 코드] 필드에 코드 입력
2. 서버가 환경변수 `ADMIN_CODE`와 대조(클라이언트 번들에 코드 미포함, 시도 5회/분 제한)
3. 관리자 UI 활성화: 전체 공지 작성(모든 화면 상단 배너, 늦게 입장해도 보임), 접속자 목록에서 강퇴
4. 강퇴된 사용자는 세션 denySet에 등록되어 즉시 재입장 차단(서버 재시작 전까지)

## 4. 아키텍처

```
브라우저 (React 19 + R3F 9)                Railway 단일 서비스 (Node 24)
┌──────────────────────────────┐  WebSocket  ┌──────────────────────────────┐
│ 입장화면(닉네임·캐릭터·색·관리자코드)   │◄──────────►│ Colyseus WorldRoom (단일 룸)      │
│ 3D 월드 (R3F, 60fps 렌더)         │ @colyseus/sdk│  · 서버 권위 상태, 10Hz patch      │
│ UI 오버레이(채팅·이모지·조이스틱·배너) │             │  · 이동 검증·채팅·공지·강퇴          │
│ 네트워크 상태는 React 밖 mutable Map│             │ express: 클라 dist 정적 서빙+SPA    │
└──────────────────────────────┘             └──────────────────────────────┘
                                               DB 없음(메모리만), PORT=env, 헬스체크
```

**모노레포 (npm workspaces)**

```
caysonverse/
├─ docs/           # 이 기획문서 등
├─ shared/         # 스키마 클래스(서버 전용 실행) + 메시지 타입/상수 (브라우저 안전 엔트리 분리)
├─ server/         # Colyseus 서버 (CJS/NodeNext, 데코레이터 tsconfig)
├─ client/         # Vite 8 + React 19 + R3F
└─ loadtest/       # @colyseus/loadtest 봇
```

- shared의 엔트리 분리 원칙: `shared/schema`(데코레이터 실행 — 서버 전용, 클라는 `import type`만), `shared/messages`·`shared/constants`(플레인 TS — 클라·서버 공용). 클라이언트 번들에 스키마 런타임 코드가 들어가지 않도록 배럴(barrel) 재수출 금지.
- 개발: vite dev(5173)에서 `/matchmake`·WS를 localhost:2567로 프록시, 서버는 tsx watch.
- 프로덕션: `vite build` → 서버가 `client/dist` 정적 서빙(+SPA fallback, `/matchmake`·모니터 경로 제외).

## 5. 네트워크 설계 (수치 검증됨)

- **patchRate = 100ms (10Hz)** — 기본 20Hz의 절반 비용. 보간으로 체감 차이 없음. 부족하면 66ms로 한 줄 변경
- **입력 모델**: 클라이언트가 자기 위치를 로컬에서 통합(조이스틱 즉각 반응) → 이동 중 10Hz로 `move {x, z, yaw}` 전송 + 정지 시 마지막 1회. 서버 검증:
  - NaN/비유한값 거부
  - 변위 ≤ maxSpeed × 경과시간 × 1.5 (순간이동 차단). maxSpeed는 **달리기 속도 `RUN_SPEED` = 걷기 4 m/s × 1.6 = 6.4 m/s** (조작 개편, 35장 — 기준 속도만 바뀌고 규칙은 그대로)
  - 보행 가능 AABB로 클램프 (맵 밖 차단)
  - 30 msg/s 초과 드롭
  - y는 서버 고정 (비행 원천 차단)
- **Player 스키마**: `nickname`(string, 입장 시 1회), **외형 15필드**(`hat`·`hatColor`·`hair`·`hairColor`·`face`·`skin`·`top`·`topColor`·`bottom`·`bottomColor`·`shoes`·`shoesColor`·`item`·`itemColor`·`voice`, 모두 uint8 — 부품 번호·색 번호이고 입장 때 1회만 쓴다. 예전의 `character`·`tint`를 대신한다, 36장), `x`·`z`(float32), `yaw`(float32), `connected`(boolean), `role`(uint8, 0 학생 / 1 선생님 — 35장). 애니메이션 상태 필드 없음 — 클라가 보간 속도로 walk/run/idle 유도(걷기·달리기 상태를 따로 보내지 않음). 채팅은 상태 저장 금지(안티패턴). `role`은 서버가 관리자 코드 인증에 성공했을 때만 1로 쓰며 join 옵션·클라이언트 메시지로는 바뀌지 않는다. **점프와 입력 중은 상태가 아니라 broadcast 이벤트**(y는 서버 고정이라 스키마에 없음, 아래 표)
- **대역폭**: 전원(100명) 이동 시 클라당 다운 ~24KB/s(≈200kbps) — 모바일 OK. 강의 모드(대부분 정지)는 델타 인코딩 덕에 5~20% 수준. 초과 시 int16 양자화 예비안
- **원격 보간**: 스냅샷 링버퍼(~10개) + 150ms 렌더 지연, yaw 최단호 lerp, 버퍼 고갈 시 250ms 외삽 후 idle, 3m 초과 이탈 시 스냅
- **기능별 전송 메커니즘**:

| 기능 | 메커니즘 | 제한 |
|---|---|---|
| 채팅 | `broadcast` | 200자, 5초당 3회(초과 시 조용히 드롭+개인 알림) |
| 이모지 | `broadcast` (uint8 인덱스) | 500ms당 1회 |
| 공지 | 루트 상태 필드 (`announcement`, `announcedAt`) | 늦게 입장해도 보여야 하므로 상태 |
| 강퇴 | `client.leave(4001)` + 메모리 denySet | onJoin에서 denySet 확인 |
| 점프 | `broadcast` `{sid}` (이벤트, y는 서버 고정) | 클라당 0.8초에 1번(초과 시 조용히 드롭), 앉은 채로는 불가. 받은 화면은 1.0 m, 0.8초 깡총 |
| 입력 중 | `broadcast` `{sid, on}` (이벤트) | 켜기는 3초에 1번, 끄기는 제한 없음(켜진 적이 있을 때만 중계). 받는 쪽은 끄기를 못 받아도 5초 뒤 스스로 끔 |

- **재접속**: `onDrop`에서 `allowReconnection(client, 20)` — 20초 창(유령의 정원 점유 최소화). `reconnectionToken`은 sessionStorage, 실패 시 이 탭이 입장 때 쓴 닉네임·외형(15필드, 메모리 — 다른 탭의 조립실이 localStorage를 바꿔 두었을 수 있어서)으로 조용히 재입장(메모리에 없을 때만 localStorage, 그 저장값이 옛 형식이면 기본 외형). 접속 끊긴 아바타는 50% 투명 렌더
- **정원**: maxClients 110 (100 + 재접속 여유), 초과 시 "정원이 가득 찼습니다" 안내

## 6. 렌더링·성능 설계 (100 아바타, 모바일 30fps 목표)

- 캐릭터 GLB **1개**(`character.glb`, 4.71MB — 뼈대 + 모든 부품 메시 + 동작 클립 13개)를 1회 로드 → 플레이어마다 **SkeletonUtils.clone()** (일반 clone은 SkinnedMesh 파손)한 뒤 **고른 부품만 남긴다**(36장). 예전의 캐릭터 GLB 4종(+ 왕관)은 삭제했다
- **조립·정점색 합치기**: 텍스처가 없는 부품(피부·머리카락·옷·신발·소품)의 색을 **정점색으로 구워 SkinnedMesh 하나로 합치고**, 텍스처가 있는 얼굴만 따로 그린다 — 예전의 클론별 `material.clone()` + 색 곱 틴트는 폐지(팔레트도 파스텔 8색 제한이 없어졌다: 옷 12색·머리 8색·피부 5색). **아바타 1명이 그리는 메시: 플레이어 2개(합친 몸 + 얼굴), AI 조교 NPC는 헤일로 같은 장식 때문에 최대 4개, 상한은 `MAX_DRAW_MESHES` = 8**. 같은 외형(`lookKey`)은 합친 지오메트리를 참조 카운트로 공유한다. 대신 부품이 많아 **아바타당 삼각형은 KayKit보다 늘었다**(실측은 `docs/loadtest.md` 7장, 아래 36장)
- **AnimationMixer 스로틀**: 카메라 <10m 매 프레임 / 10~25m 3프레임당 1회(누적 delta 전달) / >25m·프러스텀 밖·정지·착석 시 정지. 강의실 최악 케이스(전원 착석·전원 화면 안)를 이 규칙이 구제
- **닉네임표·말풍선**: canvas 텍스처 THREE.Sprite (drei `<Html>` 100개는 모바일 사망). 닉네임은 25 m부터 서서히 사라져 30 m에서 0(예전의 20 m 급숨김은 폐지), 글자 화면 높이 12~16 px로 제한, 교실처럼 사람이 많으면 화면 안 가장 가까운 15명 + 말하는 사람 + 선생님만 그린다(선택은 5 Hz, 벽 가림 검사는 프레임당 8명씩 돌려 보기 — 35장), 동시 말풍선 30개 캡
- `<Canvas dpr={[1, 1.5]}>`, 모바일 그림자 전면 off + 블롭 섀도 쿼드, 데스크톱은 1024px directional 1개까지
- 조명: hemisphere + directional 2개, Lambert/Toon 계열 머티리얼 (멀티라이트 PBR 금지)
- SkinnedMesh `boundingSphere` 수동 지정 (애니메이션 중 팝아웃 방지)
- **네트워크 상태를 React state에 넣지 않는다** — React 밖 mutable Map에 기록, useFrame에서 ref로 읽어 Object3D에 직접 반영. React state는 입장/퇴장(마운트/언마운트)과 UI 전용. (100명×10Hz = 초당 1,000 setState 방지 — 최다 실수 포인트)

## 7. 월드·에셋 (전부 CC0, 출처·라이선스 검증됨)

### 7.1 월드 구성
- 단일 맵: **라운지**(야외 광장 감성 — 소파, 커피테이블, 화분) ↔ 통로 ↔ **강의실**(대형 스크린 + 책상·의자 열)

- 강의실 대형 스크린 = 일반 box mesh (v2 화면공유 텍스처 대비)

## 8. 보안·어뷰징 대응 (익명 게스트 공간)

| 위협 | 대응 |
|---|---|
| 순간이동/스피드핵 | 서버 변위 클램프 + AABB + NaN 거부 |
| 채팅 도배 | 5초당 3회 + 200자 + 제어문자 제거 |
| 부적절 닉네임 | 길이 2~5자 + 문자셋 필터 (onJoin) |
| 관리자 코드 무차별 대입 | 서버 측 비교만(타이밍 세이프) + 시도 5회/분 제한 (IP별) |
| 강퇴 후 재입장 | 세션 denySet — 완전 차단은 계정 필요(v2 한계로 수용) |

**알려진 한계 (v1 수용):**
- 클라이언트 IP는 프록시 헤더(x-forwarded-for 등)로만 얻을 수 있어, **프록시 없는 환경(로컬 등)에서는 시도 제한이 전역 카운터로 동작**한다. 이 경우 공격자가 분당 5회 오답을 보내면 진짜 강사도 로그인이 잠길 수 있다. **Railway는 프록시 뒤에서 동작하므로 실배포에서는 IP별 제한이 정상 작동**한다 — 배포 문서에 명시할 것. **단, x-forwarded-for는 클라가 좌측 항목을 위조할 수 있으므로 서버는 신뢰 프록시(Railway 단일 홉)가 append한 _맨 오른쪽_ 홉을 실제 클라 IP로 선택한다**(server `clientIp.ts`). 신뢰 프록시가 2개 이상으로 늘면 이 "마지막 홉 = 클라" 가정을 재검토해야 한다.
- 강퇴 denySet은 **닉네임 키만** 사용한다(IP는 밴 키로 쓰지 않음). Railway 뒤에서 IP는 교실 전체가 공유하는 NAT 공인 IP이므로, IP로 밴하면 한 명 강퇴에 같은 IP를 쓰는 반 전체가 차단된다(F7). 닉네임 키는 강퇴당한 사용자의 동일 닉네임 재입장을 막으면서 다른 학생을 과차단하지 않는다. 대신 강퇴당한 사용자가 닉네임을 바꾸면 재입장이 가능하다(계정 없는 v1의 구조적 한계). IP는 관리자 코드 시도 제한(brute-force limiter)에만 계속 쓰인다.

## 9. 에러 처리·안정성

- 연결 끊김: "재연결 중..." 토스트 → reconnectionToken으로 자동 복귀 → 실패 시 조용히 신규 재입장 (지수 백오프)
- 서버 배포/크래시: 전원 접속 종료 + 상태 소실 (DB 없음 — v1 수용 리스크). 강의 시간 외 배포 원칙. 배포 전 번들이 남은 탭(옛 입장 형식 `character`·`tint`)은 재접속 때 "새 버전이 나왔어요. 페이지를 새로고침(F5)해 주세요" 안내를 받는다(36장, `docs/deploy.md` 5장)
- 화면 오류: 잡지 못한 렌더 오류(3D 장면 포함)는 빈 화면 대신 "문제가 생겼어요. 새로고침(F5)하면 다시 들어갈 수 있어요" 화면과 새로고침 버튼을 띄우고, 열린 방은 나간다(다른 사람에게 멈춘 아바타가 남지 않게). 캐릭터 GLB를 못 받으면 조립실 미리보기가 1.5·3·6초 뒤 다시 받아 보고, 입장하기가 한 번 더 받아 본 뒤 그래도 안 되면 입장하지 않고 "잠시 뒤 다시 눌러 주세요"라고 안내한다(36장)
- 정원 초과: 입장 화면에서 안내
- 헬스체크: express 라우트 (WS 엔드포인트 아님)

## 14. 의자 앉기/일어서기

### 14.1 상호작용
- **PC**: 강의실 의자 1.5m 이내 접근 시 "**E** 앉기" 안내(작은 알약 버튼, 클릭해도 됨) → **E(F도 같음)**로 착석. 앉은 상태에서 E 또는 이동키 → 일어섬
- **모바일**: 근접 시 오른쪽 아래 점프 버튼 위에 **상황 행동 버튼**(🪑 앉기)이 나타남 → 착석 후 같은 자리의 🪑 일어서기. 조이스틱을 밀어도 일어섬
- 의자와 AI 조교가 동시에 닿으면 더 가까운 쪽 하나만 제안한다(같은 거리면 앉기). 앉기·조교 대화·일어서기는 **E/F와 이 버튼이 같은 한 가지 동작**이다(35장)
- 앉으면 의자 위치에서 **스크린 방향을 향해 착석**, 일어서면 의자 뒤 통로 쪽(각 좌석별 사전 정의된 하차 지점)에 섬
- 앉은 채로 채팅·이모지·발표 시청 전부 가능

### 14.2 애니메이션 (검증 완료)
KayKit GLB 내장 클립 사용: `Sit_Chair_Down`(착석 동작) → `Sit_Chair_Idle`(앉은 자세 유지) / `Sit_Chair_StandUp`(기립 동작). 4종 캐릭터 공통 스켈레톤이므로 클립 세트 하나로 전부 동작. (⚠️ 36장: 지금은 토이 피규어 한 몸·한 뼈대, 앉기 클립 이름은 그대로)

### 14.3 서버 권위 (v1 원칙 유지)
- 좌석 데이터는 shared/worldMap의 강의실 의자 배치에서 파생: **13석** (학생 12 + 강사석 1), 좌석별 {위치, 착석 방향, 하차 지점}
- Player 스키마에 `seatIndex`(int8, -1=미착석) 추가 — 착석 상태가 전원에게 동기화 (100명 착석 장면 가능)
- 착석 검증: 좌석 인덱스 범위, **1의자 1인**(선착순, 탈락자에게 "이미 사용 중" 개인 알림), 의자와의 거리 ≤ 1.5m
- 착석 중 이동 메시지는 무시(silent drop). 일어서기는 명시적 Stand 메시지
- 좌석 반환: 일어서기·영구 퇴장·강퇴 시. 순단 재접속(20초 창)은 좌석 유지
- 하차 지점은 장애물과 겹치지 않음을 맵 불변 테스트로 보증

## 15. 화면 공유/발표

### 15.1 아키텍처
- **LiveKit Cloud**(관리형 SFU) 사용: 강사 1명이 화면+마이크 publish → 최대 100명 subscribe (지연 <0.3초)
- Colyseus(이동·채팅)와 LiveKit(미디어)는 독립 — 한쪽 장애가 다른 쪽에 전파되지 않음
- **토큰은 caysonverse 서버가 발급**: LiveKit API 키/시크릿은 서버 env에만 존재. 관리자에게만 publish 권한 토큰, 일반 사용자는 subscribe 전용 (v1 관리자 검증과 동일한 서버 권위 원칙)
- 발표 중 여부는 Colyseus 루트 스키마 상태로 동기화 (공지 배너 패턴 — 늦게 입장해도 즉시 표시)
- 서버 env 3개 추가: `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` (Railway Variables)

### 15.2 발표자(강사) UX
- 관리자 패널 [발표 시작] → 브라우저 화면 선택 창 → **화면+마이크** 동시 송출, 버튼은 [발표 종료]로 전환 + "발표 중 🔴" 표시
- 종료: 버튼 클릭 / 브라우저 "공유 중지" / 강사 접속 종료·새로고침 — 어느 경로든 전원 스크린이 원상 복귀 (LiveKit 이벤트 + Colyseus 상태 이중 정리)
- 동시 발표는 1명 (서버가 이중 발표 거부)

### 15.3 시청자 UX
- 발표 시작 시: 강의실 3D 스크린에 실시간 비디오 텍스처 + 채팅 로그에 "📽️ 발표가 시작되었습니다" 시스템 메시지
- **자동재생 정책 대응**: 소리 포함 재생은 사용자 제스처가 필요할 수 있음 → 필요 시 "발표 시청하기 ▶" 배너 1탭으로 소리까지 재생
- 스크린 클릭/탭 → 전체화면 오버레이 (X·ESC로 닫기). 시청 중 이동·채팅·이모지 정상 동작
- 수강생 재접속 시 발표 중이면 자동 재연결

### 15.4 엣지 케이스
| 상황 | 처리 |
|---|---|
| 강사 재접속 | 발표 종료 처리 → 재시작 필요 (상태 잔재 없이 정리) |
| LiveKit 연결 실패 | 스크린 평소 상태 + "발표 연결에 실패했습니다" 안내, 다른 기능 정상 |

### 15.5 비용·버전 (2026-07-16 리서치 확정 — 이 수치가 보류 결정의 근거)

- **무료 티어(Build)로는 실강의 불가**: 동시 100 WebRTC 연결 한도(강사+수강생100=101 초과), 월 5,000 참가자-분(2시간 강의 1회 = 101명×120분 = 12,120분으로 초과), 50GB 전송 — **한도 초과 시 과금이 아니라 신규 요청 실패(강의 도중 컷)**. 개발·소규모 테스트 전용.
- **실운영 = Ship 플랜 $50/월**: 150,000 참가자-분 포함(월 4회 강의 48,480분 → 여유), 250GB 포함 + 초과 $0.12/GB. 1080p15fps 화면공유(기본 2.5Mbps) 기준 강의당 90~230GB → **월 4회 강의 시 총 $63~130/월 (강의당 $16~33)**.
- **절감 레버(재개 시 설계 반영)**: 3D 스크린 텍스처는 저화질 시뮬캐스트 레이어 구독(`setVideoDimensions` 720p/360p), 전체화면 오버레이만 1080p → egress 최대 4배 절감, 월 $50~65 수준 가능. 주의: WebGL 텍스처 렌더링은 `adaptiveStream` 자동 최적화가 작동하지 않으므로(off-DOM 엘리먼트 = invisible 판정 → 트랙 일시정지 버그) `adaptiveStream: false` + 수동 레이어 지정 필수.
- 검증된 SDK (재개 시 사용): livekit-client 2.20.1(React 19 무관, 바닐라 TS), livekit-server-sdk 2.17.0(Node 24 CJS 번들 호환, `toJwt()`는 **async**), @livekit/components-react는 불필요(DOM 그리드용). 토큰 TTL 기본 6h, 연결 중 자동 갱신. 대안 비교: Daily.co ~$194/월(더 비쌈), Cloudflare Realtime ~$46/월(저렴하나 저수준 — 솔로 운영자 개발량 과다).

## 21. 모바일 1인칭 D-패드 (2026-07-16 발주자 요청)

  - **경계 채터링 방지**: 섹터 전환에 각도 히스테리시스 ±10°(업계 표준 진입/해제 문턱), 중심 반경 데드존(기존 force 0.15 규칙 상당) 이내는 정지
  - 산출 intent는 키보드와 동일한 {-1,0,1} 성분으로 기존 합산 경로에 주입 — 시선 동행·이동·네트워크 로직 무변경 (순수 입력단 교체)
- **전환 규칙**: 뷰 모드가 1인칭이면 D-패드, 그 외 조이스틱 (기존 zustand 뷰 플래그로 UI 전환). 시선 미세 조정은 기존처럼 D-패드 밖 화면 드래그

## 34. AI 갤러리 개편 + NPC 외형·음성 규칙 (2026-07-20 발주자 요청)

- **AI 갤러리**: 갤러리방의 최무호 일대기 초상 9점을 전부 내리고, 발주자 제공 AI 그림 9점(art/ 폴더 — gitignore, 웹용 변환본만 커밋)으로 재전시. 방 이름을 **"AI 갤러리"**로 변경(북벽 배너·로비 포스터·제미나이 페르소나). 큐레이터(Claude)가 감상 후 작품 제목 부여:
  1. 기하학의 마을 ② 원색의 왈츠 ③ 별바다로 가는 문 ④ 달빛 아래 학과 모란 ⑤ 금빛 산수 — 소나무와 학 ⑥ 달빛 바다와 설산 ⑦ 꽃 피는 해안의 아침 ⑧ 별밤의 바이올린 ⑨ 안개 계곡의 정자
- **전시 규격**: 눈높이 통일(높이 2m 고정), 폭은 원본 비율 그대로(가로 그림은 와이드 액자 — 상한 4.2m), 정면 포컬 슬롯(문 정면)에 가장 넓은 「금빛 산수」. 명판은 제목 카드(자동 축소 폰트). 간격·코너·문 회피 불변식은 테스트로 보장(비율 가변 폭 반영)
- **NPC 새 외형(안드로이드 조교)**: 플레이어 조립실에는 없는 모습 — (⚠️ 2026-10-31 36장으로 몸이 바뀜: 마법사 KayKit 몸 + 팔레트 교체에서 토이 몸 + NPC 전용 옷으로) 같은 토이 몸에 `npcOnly` **안드로이드 옷**(흰 웃옷·바지·신발 부품) + 어시스턴트별 **강조색** 줄무늬(아르티 오렌지/노바 그린/루미 블루/큐리 보라) + 모자·소품 없음 + **머리 위 떠 있는 헤일로 링 안테나**(절차 지오메트리, 한 번만 달린다). 머리 모양도 조교마다 달라(아르티 짧은 머리·노바 단발·루미 양갈래·큐리 곱슬) 윤곽으로도 구분된다 — 한눈에 비인간 신캐릭터
- **음성 규칙 강화**: ① NPC 음성은 **Edge TTS 전용** — 합성 실패 시 무음(브라우저 Web Speech 폴백 제거: 대화 중 목소리가 바뀌는 문제) ② 이모지 낭독 금지 ③ **ASCII/문자 그림 낭독 금지** — 줄 단위 판별(발음 가능 글자 0자 또는 기호≥글자 = 그림)로 산문만 낭독, 그림 주변의 설명 문장은 정상 낭독. 클라·서버 동일 필터(단일 소스 shared/speech.ts)
- **미로 골 챔버 NPC "큐리(Curi)"** (발주자: 길을 제대로 찾았을 때 만나는 것이 NPC): 4번째 조교를 미로 중앙 골 챔버 북측에 배치(보라 액센트) — 미로를 푼 방문자를 맞이하며 탈출 축하 + 귀환 포탈 안내가 페르소나. 골 타일·포탈·챔버 통로 무간섭은 전체 플러드필 테스트에 골·포탈 도달성 단언을 추가해 영구 보장
- **큐리 만나면 로비 귀환 (발주자 요청·2차 수정)**: **밟기 자동 포탈 제거** — 가운데 도달 즉시 포탈돼 큐리와 대화를 못 하던 문제(발주자 지적). 귀환은 큐리 대화 패널의 **"🌀 로비로 돌아가기" 버튼**이 보내는 명시적 PortalReturn 메시지로만 수행하며, 서버가 발신자가 실제로 골 챔버 안(포탈 반경 4m)에 있는지 검증 후 텔레포트(변조 클라 무력화·이동 베이스라인 리셋 유지). 포탈 패드는 시각 마커로 존치
- **NPC 외형 확정(발주자)**: 이마 바이저 바 제거 — **머리 위 헤일로 링만** 유지
- **대화 휘발성(발주자)**: NPC와 헤어지면(패널 닫힘·이탈) 그 조교와의 대화 이력은 **즉시 초기화** — 다시 만나면 인사부터 새로 시작
- **🗺/👁 토글 복원 (발주자 지적)**: 주 포인터 판정 수정(30장 후속)으로 터치 오판이던 PC가 데스크톱이 되며 터치 전용이던 🗺 오버뷰·👁 1인칭 버튼이 사라졌음 → 두 버튼을 **모든 기기 공통**으로 전환(데스크톱은 우측 이모지 팔레트 위 슬롯). M·V 키는 그대로
- **채팅 남녀 음성 (발주자 요청)**: 일반 채팅 낭독도 **Edge TTS 신경망**으로 통일 — 발신 캐릭터 성별로 목소리 선택(남: 기사·바바리안·마법사·왕·왕자 = InJoon / 여: 도적·왕비·공주 = SunHi) (⚠️ 36장: 지금은 조립실에서 고른 목소리 `voice` — 남자 InJoon / 여자 SunHi). 기존 게이트 유지(15m 거리·볼륨 감쇠·직렬 큐·대기 3건 상한·80자 클립·음소거 토글), 이모지·문자그림 필터 동일 적용, 합성 실패 시 무음(다른 목소리 금지). 서버 /api/npc-voice에 gender 파라미터 추가(캐시 키 분리), IP당 40회/분
- **모바일 채팅 레이아웃 최적화 (발주자 요청)**:
  - **일반 대화창을 맨 아래로**: 화면 중앙에 떠 있던 입력바를 하단 12px로 내림(PC와 동일). 겹침 방지를 위해 이동(조이스틱/D-패드)·이모지 팔레트를 그 위 밴드(하단 80px)로 상향, 👁/🗺/🔊 토글 열은 그대로. 소프트키보드 인셋 로직(--cv-kbd-inset)은 공유 모듈 kbdInset.ts로 추출
  - **NPC 대화창은 하단 시트로**: 우측 드로어(중앙을 가려 NPC가 안 보임) → 하단 시트(하단 ~46vh, 상단 둥근 모서리)로 전환해 위쪽에 대화 중인 NPC가 그대로 보이게 함. 대화 열려 있는 동안 루트 클래스 `cv-npc-open`으로 일반 입력바·이모지·조이스틱·D-패드·토글·채팅로그를 숨겨 몰입. 시트도 키보드 위로 상향(공유 --cv-kbd-inset). 데스크톱은 기존 우측 드로어 유지(터치 한정)

- **NPC 실체화**: 조교 3인의 위치를 맵 단일 소스(worldMap `NPC_SPOTS`)로 승격하고 각자 플레이어 크기(반경 0.4m 상당) 장애물 박스를 `OBSTACLES`에 합류 — 클라 슬라이드와 서버 이동 검증이 같은 배열로 충돌(책상·소파와 동일 취급)
- **타 플레이어 실체화**: 접속 중인 원격 캐릭터마다 매 프레임 동적 장애물 박스를 로컬 이동 해석에 합산 — 다른 사람을 통과 불가. **클라이언트 전용**(서버 검증은 정적 장애물만: 상호 접근 시 지연·보간 차로 인한 럽버밴딩 방지 — v1 관용 검증 철학 유지·문서화)
- **탈출 규칙**: 이미 겹쳐 있는 상대(스폰 스택·포탈 착지 등)는 차단하지 않음 — 걸어 나올 수 있어 영구 끼임 불가. 유령(재접속 대기 50% 투명)도 통과 가능. 프레임당 할당 0(박스 풀 재사용)

- 로비(라운지) 중앙에 대칭 응접 세트: **커피 테이블 + 러그를 중심으로 4방향 소파 링**(전 좌석이 테이블을 바라봄) + 대각 화분 2개. 기존 서측 응접 클러스터는 이 세트로 이전(서벽 긴 소파·코너 램프·화분·문 앞 화분은 유지)
- 세트 중심은 스폰 기둥의 남쪽(-15, 6.2) — **스폰 여유 반경(지터 2m + 플레이어 0.4m)과 검증된 통행 경로(z=0 서측 통로, 갤러리 동선)를 침범하지 않는 위치**로, 맵 불변식 테스트(스폰 클리어런스·통로·씰)가 자동 검증. 충돌은 기존 가구 파생 경로 그대로(서버 포함)

## 35. 조작 · 카메라 · 이름표 UI/UX 개편 (2026-10-31 발주자 요청)

- **목표·근거**: 학생이 처음 들어와서 설명 없이 **30초 안에 걷고·둘러보고·말하기**. 로블록스·제페토 등 3D 게임에 공통인 관례만 따른다(특정 게임을 베끼지 않음). 상세 근거와 출처는 `docs/superpowers/specs/2026-10-31-controls-ux-design.md`, 구현 단계는 `docs/superpowers/plans/2026-10-31-controls-ux.md`. 이 장이 앞 장들의 조작·이름표 규정보다 **우선**한다.
- **대체되는 앞 장 (⚠️ 예전 발주자 결정을 바꾼 항목)**: 5장 이동 속도 기준(걷기 → 달리기), 6장 닉네임 20 m 급숨김, 14.1장과 31장의 `T` 대화·별도 앉기/대화 버튼, 19장의 👁 중심 시점 전환 안내, 20장 1인칭 시선 동행, 21장 모바일 D-패드, 22장의 하단 UI 슬롯 배정과 34장 모바일 채팅 레이아웃의 이동·이모지 위치. 미로 골 귀환은 34장 규칙을 그대로 유지한다(행동 버튼과 E로 순간이동하지 않음).
- **PC 키**: WASD·방향키 걷기, **Shift 누르는 동안 달리기(걷기의 1.6배)**, **Space 점프**, 마우스 드래그(왼쪽·오른쪽 버튼 모두)와 Z/C 시점, **R 카메라 뒤로 정렬**, 휠 줌, 바닥 짧은 클릭 이동, **E(F도 같음) 상호작용**(앉기·일어서기·조교 대화), **Enter 또는 `/` 채팅 열기**(Enter 보내기, Esc 닫기), **1~6 이모지**, **Tab 누르는 동안 접속자 목록**, M 지도, V 1/3인칭, **Esc 메뉴**. 채팅·관리자 입력이 키보드를 쥔 동안과 자동반복에는 단축키가 반응하지 않는다(예외 Esc, Tab 떼기). 키는 모두 `game/hotkeys.ts` 한 표(`KeyboardEvent.code` 기준)에서 푼다.
- **휴대폰 조작**:
  - **왼쪽 아래 절반**: 누른 자리에 조이스틱이 생기고 손을 떼면 사라진다(다이내믹 조이스틱). 살짝 밀면 걷기, 끝까지(반경의 90% 이상) 밀면 달리기. 화면 왼쪽 가장자리 24 px 안쪽은 시스템 뒤로 가기 제스처와 겹쳐 반응하지 않는다(왼손잡이 모드는 오른쪽 가장자리). 지도(오버뷰)에서는 꺼지고 한 손가락 드래그가 지도 이동.
  - **오른쪽 화면**: 한 손가락 드래그 = 시점 회전, 두 손가락 핀치 = 줌, **두 번 톡 = 카메라 뒤로 정렬**. 바닥을 한 번 톡 = 그 자리로 걷기.
  - **오른쪽 아래**: 큰 **점프 버튼** + 그 위 **상황 행동 버튼**(근처에 의자·조교가 있을 때만, 🪑/💬) + **이모지 버튼**(누르면 6개가 반원으로 펼쳐짐). **아래 가운데**: 채팅 버튼(입력창은 키보드 바로 위에 붙음). **위쪽**: 왼쪽 위에 방 이름과 👥 접속자 수, 오른쪽 위에 👁 🗺 🔊 ☰.
  - 모든 버튼의 터치 영역은 **최소 48 px, 버튼 사이 간격 최소 8 px**(애플 HIG 44pt·WCAG 44 px 위로). PC는 오른쪽 아래에 이모지·행동 버튼을 작게 둔다.
- **1인칭 (⚠️ 20·21장 번복)**: 조이스틱·WASD의 앞뒤 = 전진·후진, 좌우 = **옆걸음**, 시선은 드래그로만 돌린다. 시선 동행을 없애 흔들림의 원인이 사라졌으므로 D-패드도 없앴다.
- **카메라**: 기본 3인칭, 머리 조금 위를 보며 부드럽게 따라간다. **저절로 돌지 않는다**(이동 방향을 따라 돌면 옆걸음 때 원을 그림) — 돌린 자리에 그대로 두고, 필요하면 R·두 번 톡으로 뒤로 정렬. **벽 뒤 당겨오기(스프링 암)**: 카메라와 캐릭터 사이에 벽이 있으면 카메라가 벽 앞으로 다가온다(최소 0.6 m, 벽 여유 0.2 m, 풀리면 초당 6 m로 복귀). 교실 의자에 앉으면 스크린이 잘 보이는 각도로 자동 전환, 일어서면 원래 시점 복귀. 지도(M)는 지금의 전체 보기를 유지(내 위치·방 이름 표시).
- **서버·네트워크**:
  - **달리기**: `RUN_SPEED` = `MOVE_SPEED` × 1.6 = 6.4 m/s. 이동 검증 예산 = `RUN_SPEED` × 경과시간 × `MOVE_SPEED_SLACK`(1.5) — 기존 규칙에서 기준 속도만 바뀜. 클라이언트는 걷기/달리기 상태를 보내지 않고, 원격 캐릭터의 걷기/달리기 동작은 보간 속도로 정한다(`Running_A` 클립, 0.800 s).
  - **점프**: y는 서버가 고정(스키마에 y 없음, 나는 핵 방지 유지). 점프는 이모지처럼 **broadcast 이벤트**(`MessageType.Jump`, `{sid}`)이고 받은 화면에서 **1.0 m, 0.8초** 깡총(`Jump_Full_Short` 클립, 1.167 s)을 보여 준다. 클라이언트당 0.8초에 1번.
  - **입력 중**: 채팅을 쓰기 시작하면 `MessageType.Typing` `{on:true}`(3초에 1번), 보내거나 닫으면 `{on:false}`. 받는 쪽은 이름표 옆에 "…"를 띄우고, 끄기를 못 받아도 5초 뒤 스스로 끈다.
  - **선생님 표시**: `Player.role`(uint8, 0 학생 / 1 선생님)을 스키마에 추가. **서버가 관리자 코드 인증에 성공했을 때만** 1로 쓴다(보조 교사 포함). join 옵션·클라이언트 메시지로는 바뀌지 않는다 — 지금까지 "관리자 여부를 다른 사람에게 보내지 않는다"던 규칙을 이 한 필드만 예외로 바꾼 것.
  - 네 가지 모두 대역폭 영향은 무시할 수준이다. 달리기·점프·입력 중을 같은 비율로 넣은 100봇 재측정은 `docs/loadtest.md` "조작 개편 재측정".
- **이름표**: 둥근 흰 캡슐(진한 글씨), 선생님은 색 테두리 + 👑 뱃지, AI 조교는 "AI" 뱃지. 글자는 화면 높이 **12~16 px** 안에 머물고(너무 작아지거나 화면을 덮지 않음), **25 m부터 서서히 사라져 30 m에서 0**(6장의 20 m 급숨김을 대체). 벽 뒤 사람은 35%까지 흐려지고(가림 검사는 프레임당 8명씩 돌려 보기), 내 이름표는 기본 숨김. **교실 100명**: 화면 안 가장 가까운 **15명 + 말하는 사람 + 선생님**만 그린다(선택은 5 Hz, 겹치면 최대 3칸 위로 비켜 쌓기). 말하면 말풍선이 이름표 바로 위에 붙고 테두리가 1초간 강조된다.
- **설정 메뉴 (Esc 또는 ☰, 브라우저 localStorage `cv-settings-v1`)**: 버튼 크기(작게/보통/크게), 왼손잡이 모드(좌우 바꾸기), 시점 감도(0.5~2배), 이름표 보기(모두 / 가까운 사람만 / 끄기), 내 이름표 보기, 조작 안내 다시 보기.
- **첫 안내**: 처음 입장하면 3단계(① 움직이기 → ② 둘러보기 → ③ 말하기). 각 단계는 실제로 해 보면 넘어가고, 건너뛰기가 있다.
- **검증**: 순수 함수 단위 테스트(조이스틱 구간·가장자리, 핀치, 이름표 선택 규칙, 서버 달리기·점프·입력 중 제한, `role` 인증 연동 등), Playwright E2E(`e2e/task-ux-desktop.mjs` 1280×800, `e2e/task-ux-mobile.mjs` 375×812 — 입장→걷기→달리기→점프→앉기→채팅→이모지), 성능 `e2e/task-ux-perf.mjs`(교실 100봇 + CPU 4배 느리게에서 이름표 시스템 프레임 비용) — 결과는 `docs/loadtest.md` 6장. **측정 결과(2026-11-01, 로컬)**: 100봇 × 630초는 서버 게이트를 전부 통과(p95 CPU 7.9%, 최대 RSS 132.8MB, 클라이언트당 다운 4.8KB/s, join 100/100, 절단·오류 0). 교실 100봇 + CPU 4배 느리게에서 이름표 시스템은 처음엔 평균 0.997~1.15 ms/프레임(기준 1.0 ms의 경계), 프레임별 p95 2.5~2.8 ms(기준 2.0 ms 초과)로 미달이었으나, 프로파일로 원인(보이지 않는 이름표까지 매 프레임 갱신, 이름표 모양이 바뀔 때마다 캔버스 다시 그리기)을 찾아 고친 뒤 평균 0.61 ms, 프레임별 p95 1.4 ms로 세 번 모두 **통과**(1배에서는 평균 0.11 ms) — 과정은 loadtest.md 6.3.1.
- **발주자 확인 대기**: 실제 휴대폰으로 30초 안에 걷기·둘러보기·말하기가 되는지, 교실 100봇 장면에서 끊김이 느껴지는지. headless 측정 fps는 참고값이고 모바일 30fps 목표는 실기기 확인으로 판정한다(`docs/loadtest.md` 6.5절).

## 36. 캐릭터 조립실 (2026-10-31)

- **무엇이 바뀌었나**: 완성 캐릭터 8종 중 하나와 색 하나를 고르던 입장 화면을, 학생이 **부품을 골라 자기만의 인형을 조립하는 "캐릭터 조립실"**로 바꿨다. 근거·결정은 `docs/superpowers/specs/2026-10-31-character-builder-design.md`(발주자 승인 완료), 구현 단계는 `docs/superpowers/plans/2026-10-31-character-stage3-integration.md`. 이 장이 캐릭터에 관한 앞 장의 규정보다 **우선**한다.
- **대체되는 앞 장 (⚠️ 예전 결정을 바꾼 항목)**: 1.1의 "프리셋 캐릭터 4종 + 색상 선택", 5장 Player 스키마의 `character`·`tint`, 6장의 GLB 4종·색 곱 틴트, 7.2의 캐릭터 에셋 행, 17장의 8종 확장, 28장의 왕실 합성(코드·자산 삭제), 30장의 "입장 화면 코스믹 배경은 유지"(밝은 하늘 정원으로 바뀜), 31·34장의 조교 몸(마법사 모델 → 토이 몸 + 안드로이드 옷), 34장의 채팅 음성(발신 캐릭터 성별 → 조립실에서 고른 목소리). 앉기 클립 이름(14장)과 걷기·달리기·점프 클립 이름(35장)은 그대로다.
- **외형 = 숫자 15개**: `hat`·`hatColor`·`hair`·`hairColor`·`face`·`skin`·`top`·`topColor`·`bottom`·`bottomColor`·`shoes`·`shoesColor`·`item`·`itemColor`·`voice`(모두 uint8). 슬롯 필드는 부품 번호, 색 필드는 팔레트 번호, `voice`는 목소리(남/여) 번호다. 범위·팔레트·기본값·프리셋·랜덤·검증은 `shared/src/appearance.ts` 한 곳이 단일 소스이고, 서버·클라이언트·봇이 모두 이것만 본다. 서버는 입장 옵션 `appearance`를 범위 검사하고(잘못된 값이면 입장 거부) 입장 때 스키마에 한 번만 쓴다 — 바뀌지 않으니 대역폭 영향은 없다. 외형은 입장 화면에서만 정한다(게임 안에서 옷 갈아입기는 v1에 없음).
- **부품 61개 + 색**: 모자 11(+없음)·머리카락 5(+없음)·얼굴 6·웃옷 12·바지 7·신발 8·손에 드는 것 12(+없음). 옷 색 12가지(금색 포함)·머리 8가지·피부 5가지, 목소리 남/여. 부품 목록과 한글 이름의 원본은 `art/character/export/character.manifest.json`이다 — `art/`는 gitignore 대상이라 main 체크아웃에만 있다. 커밋되는 것은 `scripts/sync-character-assets.mjs`가 그것으로 만든 `shared/src/characterManifest.ts`(GLB 내용 해시 `CHARACTER_GLB_HASH`도 함께 — 모델 URL이 `/models/character.glb?v=<해시>`라 새 GLB를 배포하면 캐시된 옛 GLB를 쓰지 않는다)와 `client/public/` 복사본이다. 부품 순서가 곧 외형 번호(동기화·저장되는 값)이므로 새 부품은 슬롯 끝에만 덧붙인다(append only, `appearance.test.ts`가 순서를 고정한다).
- **"Cayson 토이 피규어"**: 큰 동그란 머리·짧은 팔다리·벙어리장갑 손의 말랑한 비닐 장난감 스타일. 메시·텍스처는 블렌더로 만든 이 저장소의 오리지널 작업물이고, 뼈대(KayKit Rig_Medium)와 기본 동작 클립 7개만 CC0 KayKit에서 가져왔다. 어떤 조합에서도 뚫리지 않도록 **겹쳐 입히지 않고 몸을 구역으로 나눠 슬롯마다 자기 구역을 덮는 메시 하나로 교체**한다(웃옷 = 몸통+윗팔, 바지 = 엉덩이+다리, 신발 = 발).
- **하나의 GLB**: `client/public/models/character.glb` — 뼈대, 모든 부품 메시(`slot__id` 이름), 동작 클립 13개(기본 7 + `*_LongSkirt` 3 + `*_ShortSkirt` 3). 크기 상한은 manifest `maxBytes` = 4,718,592 B(4.5 MiB)다. 처음 목표는 3MB였으나 프리셋 차림 부품 25개를 넣으며 올렸다.
- **조립 방식**(6장): `SkeletonUtils.clone()` → 고른 부품만 남기고 → 텍스처 없는 부품의 색을 정점색으로 구워 하나로 합친다. 머리카락은 모자를 쓰면 "모자용 변형"(`hair__*__hat`)으로 바뀌고, 투구·우주 헬멧처럼 머리를 감싸는 모자(`hatHidesHair`)는 머리카락을 숨긴다. 플레이어는 메시 2개, AI 조교는 최대 4개, 상한 `MAX_DRAW_MESHES` = 8.
- **프리셋(추천 캐릭터) 8개 + 🎲 랜덤**: 왕자·공주·기사·마법사·요정·탐험가·해적·우주비행사. 기준은 발주자 결정(2026-10-31): 귀여운 아이 얼굴로도 어울리는 동화·모험 주인공만, 왕·왕비·선생님처럼 어른스러운 역할은 넣지 않고, 각자 역할에 맞는 모자·웃옷·바지·신발·소품을 모두 갖춘다. 프리셋은 부품 조합일 뿐이라 서버에는 일반 외형 15필드로 가고, 누른 뒤 자유롭게 바꿀 수 있다. 마지막으로 만든 외형은 브라우저(localStorage)에만 기억해 다음 입장 때 불러온다(옛 형식의 저장값은 기본 외형으로 대체).
- **치마 동작**: 롱스커트(공주)·치마·꽃잎 치마(요정)를 입으면 걷기·달리기·점프에서 다리가 치마를 뚫지 않도록 파생 클립을 쓴다. manifest `clipVariants`가 "하의 부품 → 기본 클립 → 변형 클립"을 정하고 `clipFor(기본 클립, 외형)`이 고른다(롱스커트 → `*_LongSkirt`, 치마·꽃잎 치마 → `*_ShortSkirt`, 나머지는 기본 클립). 로컬·원격 화면 모두 같은 함수를 쓰고, 앉기 클립은 변형이 없다.
- **조립실 화면 (Task 7b 새 디자인, 2026-11-01 발주자 요청 — 처음 화면이 "촌스럽다"는 지적)**:
  - **배경**: 밝은 하늘 정원 — 받침대가 있는 옥상 정원 그림 한 장이 화면 전체에 깔리고 그 받침대 위에 인형이 선다(발은 언제나 받침대 윗면 가운데 — 화면 크기 9가지에서 0.1 px 이내로 맞는 것을 확인했다). 넓은 화면용 1600×900과 세로 화면용 720×1280 두 장 중 **기기에 맞는 한 장만** 받고(`<picture>`, AVIF 먼저·WebP 대체, 데스크톱 AVIF 50,137 B·휴대폰 AVIF 36,652 B), 그림이 오기 전에는 약 300 B 흐림 그림(LQIP)이 깔린다. 빛 알갱이·받침대 숨쉬는 빛은 transform/opacity만 써서 움직이고 `prefers-reduced-motion`이면 모두 멈춘다.
  - **유리 패널**: 넓은 화면(≥ 900×600)은 왼쪽 유리 패널에 추천 캐릭터(🎲 + 8명, 얼굴 초상 카드)와 목소리, 오른쪽 유리 패널에 7개 아이콘 탭 레일·부품 카드·색 견본, 가운데 무대 아래에 ⟲ 이름판 ⟳와 큰 "입장하기" 버튼(이름이 유효하면 빛남)을 둔다. 위쪽 바는 Cayson 배지 + 제목, 오른쪽 위 "관리자이신가요?" 알약(누르면 코드 입력 작은 창).
  - **부품 카드의 그림은 실행 중에 그린다**: 빌드 때 굽지 않고, 미리보기와 **같은 WebGL 렌더러**로(두 번째 WebGL 컨텍스트 없음) 화면 밖 **렌더 타깃**에 찍어 비동기로 읽은 뒤 WebP로 만든다. **프레임당 최대 2장**(읽는 중인 그림이 2장이면 대기), **부품 + 지금 색으로 캐시**(상한 240장)해서 색을 바꾸면 카드도 그 색으로 다시 그려진다. 지금 탭의 카드 → 프리셋 초상 → 다른 탭 순서로 그린다. GLB가 바뀌면 그림도 저절로 맞고, 첫 화면 용량(구운 그림판 약 235 KB)을 아낀다. 그림이 없거나 실패하면 카드는 이름만 보인다. (먼저 화면 기본 프레임버퍼 귀퉁이에 그려 읽던 방식은 느린 GPU에서 미리보기가 인형 없이 나가는 일이 있어 렌더 타깃 방식으로 바꿨다.)
  - **글꼴**: 제목·묶음 이름·탭·프리셋 이름·버튼·안내는 **Jua**(SIL OFL 1.1)이고, 조립실에 쓰이는 **고정 문구의 글자만 남긴 부분집합**(76자, WOFF 18,856 B)을 `scripts/subset-builder-font.mjs`로 만들어 직접 보낸다(외부 글꼴 서버 없음, 글자 목록은 단위 테스트가 문구와 맞는지 검사). 부품 카드 이름·닉네임 입력·알림은 본문 글꼴이다(Jua로 하면 +17 KB).
  - **휴대폰 아래 시트**: 세로 화면은 위쪽 무대 + **아래 시트**(흰 유리, 손잡이로 펼치기, 안에서 스크롤: 추천 캐릭터 → 슬롯 탭 7개 → 색 → 부품 카드 → 목소리), "입장하기"는 시트 아래에 고정이다. 쉴 때 높이는 첫 부품 카드 줄이 다 보이게 정하고(390×844에서 452 px), 손잡이를 누르거나 끌면 88%까지 열린다. 무대에서 옆으로 끌면 인형이 돌고 위아래로 끌면 시트가 스크롤된다. 모든 터치 대상은 44 px 이상. 태블릿·가로 휴대폰은 같은 시트가 오른쪽 패널이 된다. 화면 크기 → 배치는 `stageLayout()` 순수 함수 하나가 정한다.
  - **용량**: 조립실 새 디자인이 첫 접속에 더한 바이트는 약 119 KB(배경 + 글꼴 + 아이콘 + CSS + JS, 예산 120 KB 이내).
- **조립실은 모든 체험이 같이 쓰는 Caysonverse 입구다 — 학교 이름이나 장식을 넣지 않는다.** 방탈출 "AI 학교 탈출"은 Caysonverse 안의 체험 하나이고 현재 월드를 대체하지 않는다(2026-11-01 발주자, 탈출 설계 14장 "기존 월드와 다른 체험"). 체험이 둘 이상이 되면 입장 화면에 "어디로 갈까요?"를 둔다.
- **배경 그림의 출처와 이용 확인**: 배경은 **ChatGPT(OpenAI) 이미지 생성, 발주자 계정, 2026-11-01**(A안)으로 만들고 글자 같은 무늬는 손으로 지운 뒤 AVIF·WebP로 줄였다. **상업 판매(학교 판매 라이선스)에 써도 되는지는 2026-11-02에 OpenAI 이용약관(2026-01-01 시행분)으로 확인했다 — 상업적 이용은 허용되고, 그림은 배타적이지 않으며, 사람이 만든 것처럼 소개하지 않는다**(`docs/licenses.md`와 `client/public/models/LICENSE.md`에 같은 내용으로 적었다. 약관이 바뀌면 다시 확인하고, 학교 판매 계약 같은 최종 판단은 발주자가 한다). 로고(`cayson-logo-white.png`, Fredoka 700 OFL)는 조립실 제목에만 쓰고 모자·옷 부품에는 넣지 않는다(발주자).
- **AI 조교 NPC**: 같은 토이 몸에 NPC 전용 `android` 옷(흰 웃옷·바지·신발) + 조교별 강조색(아르티 오렌지·노바 그린·루미 블루·큐리 보라) + 머리 위 헤일로 링 + 조교마다 다른 머리 모양. 이름·위치는 그대로(31·34장). 플레이어와 같은 조립 경로를 쓰므로 NPC 전용 모델·텍스처는 없다.
- **정리**: KayKit 캐릭터 GLB 4개·왕관 GLB·`royalPalette`·`royalAttachments`·`CHARACTER_COUNT`·틴트 상수를 삭제했다. 빌드 결과물 `client/dist`는 24.1 MB에서 9.8 MB로 줄었다(Task 9에서 9.6 MB, 조립실 새 디자인의 배경·글꼴이 더해진 지금 9,843,871 B).
- **검증**: 단위 테스트(외형 범위·직렬화·manifest와 GLB 메시 이름 일치·`clipFor`·합치기·스킨 값·조립실 배치 `stageLayout`·카드 그림 스케줄러·글꼴 글자 목록), 렌더 점검(슬롯별 모든 종류가 나오는 13개 조합과 랜덤 조합을 앞·옆·뒤에서, 프리셋 8개를 서기·걷기·달리기·점프·앉기 자세로 찍어 뚫림·떠 보임 확인), `e2e/task-char-builder.mjs`(조립실 → 입장 → **다른 화면에서 같은 외형이 보이는지** → 치마 동작 → 재접속 → 옛 저장값 → 휴대폰, 134개 점검), 캐릭터 GLB 받기 실패 `e2e/task-char-glb-retry.mjs`(503으로 막으면 미리보기가 다시 받기 → 입장하기가 막히고 안내 → 풀면 입장, 월드 안에서 실패하면 오류 화면 + 방 나가기, 25개 점검), 용량·성능 `e2e/task-char-load.mjs`·`e2e/task-char-perf.mjs`, 부하 `loadtest/`(봇이 랜덤 외형으로 입장).
- **측정 결과 (2026-11-02, 로컬 — 과정과 원본은 `docs/loadtest.md` 7·8장)**:
  - **첫 접속 8,216,208 B(7.84 MiB)** — 8 MiB 게이트(8,388,608 B) 안이고 KayKit 때의 17.03 MiB에서 54% 줄었다. `character.glb` 4,713,236 B(상한 4,718,592 B), 옛 GLB 요청 0건. 여유는 얇다(전체 172,400 B, GLB 5,356 B).
  - **교실 100명 렌더**(휴대폰 375×812, CPU 4배 느리게 headless, 3회 평균, KayKit와 나란히): draw calls **274.65**(770.43), fps **24.25 / 하위 5% 19.93**(12.79 / 11.30), JS heap 189.3 MiB(175.4), **삼각형 820,111(315,949의 2.6배)**. 아바타당 평균 15,845 삼각형, 메시는 플레이어 2개·조교 4개(상한 8).
  - **삼각형이 늘어난 것은 예상한 대로이고 이번 단계에서 고치지 않았다.** headless fps는 CPU 쪽 비용(draw call)에 민감하고 삼각형 비용은 보지 못했을 가능성이 크므로, 실기기에서의 영향은 발주자의 휴대폰 확인으로 본다. 줄이는 선택지(별도 작업): 2단계 자산에 Decimate를 적용해 아바타당 약 8천 삼각형으로, 또는 먼 아바타 LOD.
  - **100봇 × 30분**(월드 전체, 봇은 랜덤 외형으로 입장): p95 CPU 7.8%, 최대 RSS 185.8MB, 클라이언트당 다운스트림 4.7KB/s, join 100/100, 절단·오류 0 — 서버 게이트 전부 통과. RSS는 8분 뒤 129~133MB에서 평탄하다가 28분쯤 185MB로 한 단계 올랐다(원인 미조사, 게이트 400MB의 절반 이하).
- **알려진 모델 한계 (발주자 결정 몫)**: 렌더 점검에서 찾은 가벼운 문제들이다 — ① 멜빵 상의·끈이 마법사 로브·꽃잎 원피스 위로 그려져 "로브 위에 멜빵바지"처럼 보이는 조합이 있다, ② 마법사 로브 옆판이 앉기·달리기에서 작은 날개처럼 벌어진다, ③ 티아라를 옆에서 보면 가는 막대처럼 보인다, ④ 곱슬머리의 모자용 변형은 머리띠류(고양이 귀 머리띠·티아라·꽃 화관) 아래 정수리에 옅은 이음매가, 짧은 머리의 모자용 변형은 목덜미에 곧은 끝선이 보인다. 코드 문제가 아니라 모델 수정 사항이라 이번 단계에서는 고치지 않았다.
- **발주자 확인 대기**: 실제 휴대폰에서 ① 조립실을 쓸 수 있는지, ② 교실 100봇 장면이 끊기지 않는지(30fps). 헤드리스 측정 fps는 참고값이다. 30fps에 못 미치면 첫 후보는 아바타당 삼각형(KayKit보다 늘었다)이고, 선택지는 2단계 자산에 Decimate를 적용해 아바타당 삼각형을 줄이는 것(별도 작업)이다. 결과는 `docs/loadtest.md` 7.5절에 한 줄로 남긴다.

## 37. AI 학교 탈출 1단계 (2026-11-02)

- **무엇을 만들었나**: Caysonverse 안의 체험 하나인 **AI 학교 탈출** — 한 반(최대 100명)이 2~6명 팀으로 나뉘어 푸는 AI 윤리 협동 방탈출이다. 이야기: 학교 축제 전날, 학교 AI "아리"가 인터넷에서 잘못 배운 나쁜 습관 7가지로 교실 7곳을 잠가 버렸다. 팀이 퍼즐로 그 습관 하나를 바로잡고 마지막 문에서 알맞은 윤리 원칙으로 아리를 설득하면 탈출한다. 길잡이는 손전등을 든 경비 로봇 "반딧"이다. **1단계는 기반 전체와 시범 교실 "상담실"(아리의 습관: 비밀을 아무에게나 말함, 주제: 개인정보·프라이버시) 하나까지다.** 나머지 교실 6개(도서관·방송실·진로실·미술실·과학실·미디어실)는 2단계이고, 중앙 홀에서 그 문들은 "준비 중" 표지와 함께 닫혀 있다(`PHASE1_OPEN_ROOMS`). 7개 교실을 모두 마친 뒤의 중앙 홀 피날레, 순위판, 효과음과 음악도 1단계에는 없다. 근거·결정은 `docs/superpowers/specs/2026-10-31-ai-school-escape-design.md`(스펙), 구현 단계는 `docs/superpowers/plans/2026-10-31-escape-phase1.md`(계획)다. 지금 월드(라운지·강의실·갤러리·미로·AI 조교 4명)는 **대체하지 않고** 그대로 둔다(스펙 14장 "기존 월드와 다른 체험", 36장).
- **입장 화면 (⚠️ 36장의 입장 흐름을 바꾼 항목)**: 조립실에서 "입장하기"를 누르면 곧바로 월드로 들어가던 것이 이제 "어디로 갈까요?" 시트를 거친다. 카드는 지금 **AI 학교 탈출 하나**다 — 학생은 반 코드 6자리, 선생님은 시트 안 "선생님이신가요?"에서 선생님 키와 글 수준을 넣고 "반 열기". 지금 월드는 입장 화면에서 **숨기고**(`SHOW_WORLD_ON_ENTRY = false`, `client/src/ui/entryForm.ts`) `?world=legacy` 주소로만 예전 그대로 들어간다(관리자 코드 알약도 거기서만 보인다). 발주자 결정은 스펙 14장 "2026-11-02 발주자 결정".
- **방 구조 (서버)**: 방 세 종류가 같은 `PlayerRoom`(이동 검증·채팅·이모지·점프·입력 중·재접속) 위에 올라간다.
  - **`ClassRoom`**(방 이름 `class`) — **반 코드 하나에 방 하나**. 중앙 홀과 동쪽 복도의 이동·채팅, 팀, 수업 단계(`lobby → running ⇄ paused → ended`), 선생님 명령, 결과를 맡는다. 반마다 홀이 따로라 다른 반 학생은 서로 보이지 않는다.
  - **`EscapeRoom`**(`escape`) — **팀 하나에 방 하나**. 퍼즐 상태·가방·타이머·힌트·팀 채팅을 맡는다. 같은 교실을 여러 팀이 동시에 풀어도 서로 만나지 않는다.
  - **`WorldRoom`**(`world`) — 지금 월드 그대로(위 `?world=legacy`).
- **교실에 들어가는 길 = 1회용 입장권**: 문 앞 발판에 팀원이 2명 이상 모이면 먼저 모인 팀장이 "입장"을 누른다. 반이 그 팀의 `EscapeRoom`을 만들고 팀원마다 **1회용 입장권**을 준다 — 60초 안에 써야 하고(`TICKET_TTL_MS`) 그 팀원의 반 신원에 묶여 있어 다른 사람이 쓸 수 없다. 팀원은 입장권으로 교실에 접속하되 반 연결은 그대로 두고, 홀에서는 "교실 안"(`Player.place`)으로 표시되어 그려지지 않는다. 교실의 자리는 13석(팀 최대 6명의 끊긴 자리 + 새 접속 6 + 여유 1)이라 한 팀이 한꺼번에 새로고침해도 방이 차지 않는다. 새로고침한 사람은 같은 반 코드와 닉네임으로 다시 들어오면 자기 교실로 저절로 돌아가고(같은 가방·같은 나눠 보기 몫), 교실을 나오면 홀로 돌아온다. 빈 교실은 2분 뒤 정리된다.
- **반 코드와 선생님 키**:
  - **반 코드**: 6자리, 헷갈리는 글자(0/O, 1/I)를 뺀 32가지 글자. 그 수업 동안만 유효하다.
  - **선생님 키**: 계정이 없으므로 운영자가 선생님마다 키를 발급한다(`scripts/teacher-key.mjs`가 `XXXX-XXXX-XXXX-XXXX` 모양을 터미널에 한 번만 보여 주고 파일에는 sha256 해시만 둔다 — `docs/deploy.md` 8장). 선생님이 키로 반을 열면 `POST /api/class/teacher`가 반 코드와 **2분짜리 1회용 `teacherPass`**를 주고, 그 입장권으로 반에 선생님(`role` 1)으로 들어간다. 키는 HTTP 본문으로만 오가며 게임 접속에는 실리지 않는다. 틀린 키는 IP당 1분에 5번까지(넘으면 429).
  - 같은 그룹(`group`)의 선생님끼리는 서로의 반에 들어갈 수 있다(교대·보조 교사). `ADMIN_CODE`는 **운영자 키**로 남아 어느 반이든 열 수 있고, `POST /api/operator/status`로 열린 반·인원·팀·교실 수와 서버 상태(메모리·CPU·이벤트 루프 지연)를 본다.
  - **수명**: "수업 끝내기" 뒤 결과 CSV를 받을 30초(`CLASS_END_GRACE_MS`)가 지나면 연결을 닫고(닫는 코드 4102), 마지막 사람이 나간 뒤 10분이 지나도 닫힌다. 서버를 다시 켜면 열려 있던 반과 교실은 모두 사라진다(DB 없음 — 수업 중 배포 금지). 서버 하나가 동시에 여는 반은 `CV_MAX_CLASSES`(기본 `MAX_CLASSES_DEFAULT` = 10)까지다.
- **팀**: 한 수업 동안 유지된다. 홀의 팀 칸에서 만들고 2~6명(권장 4명)이며, 이름은 정해진 목록(12개 이름 × 8개 색, 예 "햇살(파랑)")에서만 고른다 — 자유 입력 없음. 한 반에 팀은 50개까지. 선생님은 "자동 배정"(팀 없는 학생)과 "섞기"(교실에 들어가지 않은 팀)를 쓸 수 있다.
- **퍼즐 엔진**: 교실 하나 = 서버 전용 데이터 파일 하나(`server/src/escape/rooms/<id>.ts`, 1단계는 `counsel.ts`). 공용 엔진(`engine.ts`·`coop.ts`)이 이 데이터를 읽어 **서버에서** 상태를 바꾸고 검증한다. 엔진은 순수 함수이고 시간은 `GameClock` 하나로만 흘러서 시간 규칙을 시계 없이 시험한다. 상태는 서버가 정해 팀원 모두에게 똑같이 보이고, 늦게 들어오거나 다시 접속한 사람도 현재 상태를 그대로 받는다(`projection.ts`). 상담실은 퍼즐 단계 5개(단계마다 힌트 3개)다.
  - **자물쇠**: 숫자·글자(바퀴)·분류판(카드를 "공개해도 돼요 / 멈춰요"로 나누기). 같은 팀의 제출은 1.5초에 한 번(`LOCK_SUBMIT_GAP_MS`), 한 클라이언트가 초당 10번(`ESCAPE_ACTION_RATE`)을 넘기는 퍼즐 동작은 버린다. 틀린 시도는 세어 별에 반영한다.
  - **조사·가방·조합**: 물건을 조사하면 확대 화면(기울이기·뒤집기·자외선 손전등)이 열리고, 주운 물건은 팀 공용 가방에 들어가 누구나 꺼내 쓰고 합친다(손전등 + 보라색 필름 = 자외선 손전등).
  - **협동 스위치(동시 누르기)**: 두 사람이 2초 안에(`COOP_WINDOW_MS`) 각자의 스위치를 눌러야 열린다. 접속한 팀원이 혼자면 3초 길게 누르기(`SOLO_HOLD_MS`)로 바뀐다. **나눠 보기**: 단서의 반쪽씩을 서로 다른 팀원에게 보여 줘 채팅으로 맞춰야 한다(혼자면 둘 다 보인다).
  - **설득 투표(마지막 문)**: ① 알맞은 윤리 원칙 고르기 ② 아리에게 할 말 고르기를 **접속한 팀원 모두가 같은 선택**으로 모아야 문이 열린다(만장일치). 틀리면 그 원칙이 왜 맞지 않는지 짧은 설명을 보여 주고 30초(`FINALE_COOLDOWN_MS`) 뒤 다시 고른다. 원칙별 "첫 시도 정답/오답"이 결과 CSV에 남는다.
  - **글 수준 두 단계**: 선생님이 반을 열 때 "쉬운 말 / 조금 어려운 말"을 고르고(`TextLevel` = `easy`/`hard`), 교실의 문구는 두 문장을 짝으로 갖는다. 같은 반의 모든 팀이 그 단계를 쓴다.

    - **홀 화면 성능**(휴대폰 375×812, "가볍게", CPU 4배 느린 headless — 참고값): 반 **30명** 홀은 프레임 평균 **23.3 / 23.9 ms**(약 42 fps, 게이트 ≤ 33 ms)·p95 30.4~30.5 ms·이름표 0.4 ms로 **휴대폰 예산을 통과한다.** 한 반에 **100명**을 몰아 넣으면 평균 **62.3 / 60.0 ms**(약 16 fps)로 **통과하지 못한다**(스로틀 없이는 10.6 ms). 실제 반은 25~30명이고 반마다 홀이 따로이므로 100명 한 홀은 스트레스 경우다. 원인 후보는 36장과 같은 아바타당 삼각형(홀의 100명 ≈ 63~78만)이고, 줄이는 선택지(아바타 Decimate, 먼 아바타 LOD)는 2단계 작업이다. 상담실 안(6명 이하)은 평균 8.8~9.2 ms(약 109~113 fps)로 여유가 크고, PC "화려하게"는 홀 60.8 fps·상담실 62.4 fps다(headless GPU라 행끼리만 비교).
- **최종 수정 (2026-11-02, 브랜치 전체 리뷰 뒤)**:
  - A1 수업 끝 CSV: "끝내기"를 누르면 서버가 모든 교실의 결과(아직 탈출하지 못한 팀 포함)를 모은 뒤 접속한 선생님 모두에게 최종 CSV를 보낸다(`ResultsCsv`의 `final`). 브라우저는 반마다 한 번만 "…_최종.csv"로 저장한다. 끝내기 창은 "끝내면 모든 팀의 최종 결과 CSV를 자동으로 받아요."라고 말한다.
  - A2 선생님 다시 들어가기: 선생님 양식에 "이어서 들어갈 반 코드"(선택)가 있고, 이 브라우저가 마지막으로 연 반(3시간 이내, `cv.teacherClass`)으로 미리 채워진다. 코드를 넣으면 **그 반**의 입장권을 받고 새 반은 열지 않는다(같은 닉네임이면 끊긴 선생님 자리를 이어받는다). 열려 있지 않거나 끝난 반은 "그 반 코드는 지금 열려 있지 않아요. 새 반을 열려면 반 코드를 비워 주세요"(404)로 거절한다. 들어갈 수 있는 키는 위 규칙 그대로다(연 선생님, 같은 그룹 선생님, 운영자). 서버 재시작 복구만 `reopen: true`로 같은 코드를 다시 연다. 입장권 요청은 10초가 지나면 네트워크 오류 문구로 끝난다.
  - A3 잠든 휴대폰: 반과 팀 교실의 재접속 창은 **180초**(`CLASS_RECONNECT_WINDOW_S`), 지금 월드는 그대로 20초다. 그동안 팀원에게는 반투명 유령으로 보이고 교실 퍼즐은 그 사람을 빼고 센다(혼자 모드 등). 180초가 지나야 팀에서 빠진다. 반에서 화면 오류가 나도 동의한 나가기를 하지 않아 팀을 잃지 않는다.
  - B1 반의 팀 메시지(만들기·들어가기·나가기·자동 배정)와 문 메시지(입장·교실 다시 들어가기)·결과 요청은 클라이언트마다 1초에 10번(`CLASS_ACTION_RATE`, 퍼즐 동작과 같은 값)을 넘으면 버린다.
  - B2 반 만들기가 20초(`CREATION_TIMEOUT_MS`) 안에 끝나지 않으면 그 요청은 500으로 끝나고 예약한 반 코드와 반 자리를 돌려준다.
  - B3 "섞기"의 대상이 2명(`TEAM_MIN`)보다 적으면 아무것도 바꾸지 않는다(혼자인 팀을 풀어 팀 없는 학생을 만들지 않는다).
  - B4 탈출한 교실은 그 교실이 아직 열려 있는 동안(빈 교실은 2분 뒤 닫힘)에도 다시 들어갈 수 없다: 서버는 "이미 탈출한 교실이에요", 문 앞 안내는 "이미 탈출했어요 ⭐×n"이다.
  - B5 반딧 다듬기(`BANDIT_AI=1`)가 던지거나 실패하면 정해진 힌트 문장을 그대로 보낸다(힌트가 사라지지 않는다).
  - B6 상담실 모델을 다 받기 전에 교실을 나가도 `counsel.glb`와 라이트맵이 로더 캐시에서 비워진다(교실 장면이 나갈 때 비운다).
  - B7 `?debug=colliders`는 개발 빌드(`import.meta.env.DEV`)에서만 켜진다.
  - B8 Draco 디코더 옆에 Apache License 2.0 전문(`client/public/draco/LICENSE.txt`)을 함께 보낸다(`docs/licenses.md`).
- **알려진 한계·남은 일**:
  - Oracle 부하 측정 전이고 100명 한 홀은 휴대폰 예산을 넘는다(위). 30fps의 최종 판정은 발주자의 실제 휴대폰이다.
  - 상담실의 살펴보기 확대 화면은 보라색 베일을 덮어 PC에서 밝기 평균이 0.395~0.439로 기준 0.45에 못 미친다(Task 24 측정). 방 장면 자체는 모두 통과하고 베일은 고치지 않았다.
  - 학교 GLB·라이트맵 주소에는 캐릭터 GLB와 달리 내용 해시(`?v=`)가 없다. GLB와 충돌 목록(`hubColliders.ts` 등)이 배포 틈에 어긋나지 않게 서버와 클라이언트를 연달아 배포한다(`docs/deploy.md` 0장).
  - 반딧 힌트의 Groq와 채팅 낭독의 Edge TTS는 판매 전에 정식 상용 계약이나 대체 수단을 정한다(스펙 10장). 기본값은 AI 없이 정해진 힌트다(`BANDIT_AI=0`).

### 발주자 확인

- 발주자는 **배포 뒤 운영 서버에서 직접 플레이**해 보기로 했다(2026-11-02 승인). 1단계를 main에 합쳐 Oracle(서버)과 Vercel(클라이언트)에 배포한 다음, 발주자가 `https://caysonverse.vercel.app`에서 선생님 키로 반을 열고 휴대폰·다른 브라우저로 학생 2명 역할을 넣어 상담실을 끝까지 탈출해 본다. **그 결과를 이 절에 적는다.**
- 확인할 것: 12~15분 안에 끝나는지, 협동이 꼭 필요하다고 느껴지는지, 문장 수준(쉬운 말 / 조금 어려운 말), 밝기("밝은 낮"), 휴대폰에서 끊김 없이 30fps로 느껴지는지, 화려함, 아이에게 맞는 내용인지, 반 30명 정도의 홀에서도 끊기지 않는지.
- 결과: **확인 대기.** 발주자가 플레이한 뒤 발주자의 말을 그대로 여기에 적고, 고칠 것을 목록으로 만든다. "상담실 OK"가 나오기 전에는 2단계(나머지 교실 6개)를 시작하지 않는다(스펙 11·12장).

## 38. 케이슨 마을 1단계 (2026-11-03 ~ 11-09)

기획 원문은 `docs/superpowers/specs/2026-11-03-cayson-village-design.md`(12장이 1단계 범위)다. 이 장은 **만든 결과와 알려진 한계**를 적는다. 1단계는 결제·로그인이 없는 **구경 버전**이다(발주자 결정, 2026-11-03).

### 38.1 의도

- 케이슨 마을은 한적한 시골 마을을 사실적으로 만든 3D 공간이고, **건물을 하나씩 지으며 넓혀 가는 마을**이다. 첫 건물은 반려동물 추모관(봉안당)이다.
- 발주자는 장난감 같은 첫 시안을 "허접"이라며 거절했고, 실제 봉안당·시골 마을 사진(Aside로 매번 찾아봄)을 기준으로 사실적으로 만들었다.
- "AI 학교 탈출"은 보류한다(상담실 OK 전). 마을의 한 경험으로 남고, 입장 화면과 방 구조는 한 경험에 묶이지 않게 만들었다.
- 결제·회원·소품 가게·사진 올리기·검수·약관은 2단계다. 1단계의 추모관 칸은 예시 칸이고, 촛불은 저장되지 않는 연출이다.

### 38.2 1단계에 들어간 것

- **마을 광장**: 지름 약 60 m 포장 광장과 지름 약 16 m 분수, 둥근 길, 개울과 나무다리, 벚나무·꽃밭·가로등, 빈 부지(빛나는 경계선과 "곧 지어져요" 표지판), 먼 산·폭포·호수. 처음 들어오면 분수 광장에서 시작한다. 한 방(샤드)은 30명이다.
- **반려동물 추모관**: 지붕과 천장이 있는 건물. 문으로 들어가면 실내 카메라로 바뀌고 호실에 칸 벽(266개 앵커)이 있다. 예시 칸(약 60%)과 빈 칸이 섞여 있다. 예시 칸 앞에서 E를 누르면 사진·이름·글 카드가 열리고, 빈 칸은 "곧 이 자리에 우리 아이를 모실 수 있어요"를 보여 준다. 촛불은 칸에서 바닥 위 거리 1.5 m 안에서 켤 수 있고, **추모관 안 사람에게만** 보인다. 칸이 비어 있으면 서버가 거절한다. 추모관 안은 조용한 구역이라 이모지·점프가 막힌다.
- **실제 한국 시각의 낮과 밤**: 해와 하늘은 실제 한국 시간과 날짜(해 뜨고 지는 시각 포함)를 따른다. 서버가 5분마다 시각을 보내 폰 시계가 틀려도 같은 하늘을 본다(재접속 때도). 밤에는 가로등·창·분수·추모관 유리창에 불이 켜진다. 밤 라이트맵은 밤이 가까울 때만 받는다.
- **안내 NPC와 AI 음성**: 마을 안내원과 추모관 안내 데스크 두 명이 각 4개의 질문·답을 갖고 있고, 문의한 사람에게만 음성이 재생된다. 음성 8개는 VoxCPM2(Apache-2.0)가 글 설명으로 새로 디자인한 목소리이며 실제 사람 목소리 복제는 없고 대화창에 "AI 음성"을 표시한다(`docs/licenses.md`).
- **배경음악(BGM)**: 발주자가 Suno로 만든 오리지널 곡 하나(96 kbps mp3, 2,157,296 B). 첫 터치·키 입력에서 시작하고 ♪ 버튼으로 끈다(기억됨). 추모관 안에서는 작아지고, 안내 음성 중에는 줄어든다. 숨은 탭에서는 멈춘다. 이동은 Web Audio GainNode로 하고 iOS는 모든 터치와 `statechange`에서 `resume()`을 건다.
- **터치 목표**: 휴대폰 버튼은 모두 48 px 이상·간격 8 px 이상이고 PC HUD 버튼이 겹치지 않는지 e2e가 검사한다.
- **카메라·조작**: 지금의 걷기·클릭 이동·조이스틱을 그대로 쓰고, 추모관 안에서는 천장 아래 카메라(최대 높이 3.0 m)·모서리 시점 보정을 쓴다. 가 볼 곳 시트("추모관 가기" 등)로 빠르게 이동한다.

### 38.5 알아 둘 판단(결정)

- 마을 색: ACES 톤매핑이 어두운 나무를 뭉갰기 때문에 마을은 Neutral 톤매핑(노출 1.4)과 주변광 보정을 쓰고 광장 허브는 ACES 그대로다(다시 굽지 않음).
- 추모관 카메라 최대 높이는 3.0 m다(천장 3.3 m − 여유 0.3 m, 기획의 3.1 m는 여유와 충돌). 머리 위 10 cm가 줄었다.
- 촛불 거리는 칸 중심이 아니라 **바닥 위 거리(열 기준) 1.5 m**로 잰다. 이름 카드는 판에 닉네임(by=닉네임)을 그대로 쓰고 평면 3D 카드로 둔다.
- "지어질 거예요"·"곧 준비하고 있어요"는 가격·날짜를 말하지 않는 부드러운 문구라 그대로 둔다. 발주자가 반대하면 음성 2개를 다시 만든다.
- 음성 엔진은 VoxCPM2(발주자 PC, 오프라인, 호출 비용 0). 사람 목소리는 복제하지 않는다.
- 가까운 쪽이 이기고 동점이면 안내원이 이긴다(문이 닿는 거리여도). 안내 데스크는 문 앞 겹침을 줄이려고 (302.8, 3.0)으로 옮겼다.
- 마을 보이는 인원 30명은 휴대폰 성능 때문이며, 아바타 LOD 뒤에 50~100명을 검토한다.
- 밤 라이트맵 로드·1024 제한은 모든 단계에 적용된다(바이트도 줄이는 쪽).

### 38.6 알려진 한계 · 발주자 메모

- **실제 아이폰 확인이 필요하다**: 소리(무음 모드, 잠금·해제, 전화 수신)와 메모리(Safari Web Inspector → Memory)는 에뮬레이션으로 알 수 없다. 배포 전 발주자 확인 항목이다.
- **iOS 요소 대체 재생은 음량이 고정**이다. Web Audio가 끝내 `running`이 되지 않으면(멈춘 뒤 2.5초) 연결 안 된 요소로 재생하는데, iOS에서는 음량을 못 바꿔 그때는 BGM이 최대 음량이고 페이드·추모관 낮춤·음성 낮춤이 듣지 않는다(드문 경우).
- 라이트 단계 1024 제한은 원본 텍스처를 바꾸므로, 방문 중 그래픽 설정을 낮음 → 높음으로 바꾸면 이미 올라간 1024 텍스처는 마을 파일을 놓을 때까지 그대로다.
- **늦게 들어온 사람은 이미 켜진 촛불을 보지 못한다**(저장 없는 연출이라 의도한 것, Task 9 판단). 들어온 뒤 켜진 촛불부터 보인다.
- **N3(사소, 받아들임)**: 밤 라이트맵이 받는 도중 마을을 놓고 곧바로 다시 잡으면 두 번 받을 수 있고, 받는 도중 밤이 끝나면 장면이 닫힐 때까지 캐시에 남는다. 둘 다 눈에 보이지 않는다.
- **시각 다듬기 목록**(범위 밖): 따뜻한 톤, 천창(하늘빛), 안내 데스크 가구, 벚나무 카메라(휴대폰에서 카메라가 벚나무 잎 안에 들어갈 수 있음), 한낮 광장, 눈 덮인 산·먼 숲 색, 남쪽 둑이 비어 있음, 개천 수면(개요 화면), 사진 실루엣이 검음.
- **예시 칸이 위치로 뭉친다**: 예시 칸은 근접한 id의 FNV 해시로 정하므로 한 줄에 몰린다(예: 북쪽 3행 0~9열은 차 있고 10~19열은 비어 있음). 1단계 이전부터 그랬고 바꾸지 않았다.
- 👥 인원 수는 내 구역(마을 또는 추모관) 사람만 센다.
