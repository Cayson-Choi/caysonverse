## 2. 기능별 흐름 (PC / iPhone 13 세로)

### F1. 기일·생일 알림과 그날 칸 장식

**가족이 정하기**
- 모시기 마지막 단계(1차 설계 2장 9번 ④ 미리보기 뒤)와 칸 카드 [정보] 탭에서 "기억하고 싶은 날" 시트가 열려요(시안 `mockup_phone_share_remind.png` ②).
  - 생일, 무지개다리 건넌 날: 모시기 때 넣은 날짜를 그대로 보여 줘요. 날짜를 모르면 "날짜 모름"이 기본이고 그 날은 꺼져 있어요. 연도만 모르는 것도 돼요(월·일만으로 장식).
  - 49일·100일: 건넌 날에서 계산해요. 처음 한 해에만 있어요. 기본은 꺼짐이에요(종교·가정마다 달라서).
  - 추모식에서 이름 불러 주기(F4 연결): 기본 켜짐은 **기일이 있는 주만**이에요. 꺼도 돼요.
  - 장식을 다른 방문객에게 보일지: 기본 켜짐. "조용히 보내고 싶어요"를 고르면 가족 기기에만 보여요.
- 알림 받는 법(계정이 없어도 되는 방법만):
  1. **[내 휴대폰 달력에 넣기]** (추천, 기본 버튼): 기기에서 바로 `.ics` 파일을 만들어 내려받게 해요. 생일·기일은 매년 반복(`RRULE:FREQ=YEARLY`), 하루 전 오전 9시 알림(`VALARM`). 파일 안에는 공유 링크(F6)가 들어가서 알림을 누르면 칸으로 와요.
     - iPhone Safari: 내려받으면 "캘린더에 추가" 창이 떠요. PC: 기본 달력 앱(Outlook·구글 캘린더 가져오기)으로 열려요.
     - 이름과 날짜는 **이 기기 안에서만** 파일로 만들어져요. 구글 캘린더 주소에 이름을 붙여 보내는 방식은 쓰지 않아요(개인 정보가 주소에 남음).
  2. **[마을에 들어올 때만 알려 주기]**: 이 기기가 주인인 칸의 날짜를 기기에 기억해 두고(localStorage, 실패해도 게임은 동작), 그날 ±3일 안에 마을에 들어오면 화면 위에 조용한 띠 한 줄: "내일은 콩이의 생일이에요 · [칸 보러 가기]". 하루 한 번만 떠요.
  3. (나중, 계정 뒤) 웹 푸시·카카오 알림톡. iPhone 웹 푸시는 홈 화면에 앱을 추가해야만 되기 때문에 처음 온 사람에게 맞지 않아요. 계정이 생긴 뒤에 다시 판단해요.

**그날 칸에서 일어나는 일 (한국 시간 00:00~24:00)**
- 서버가 하루 한 번(자정, 그리고 서버가 켜질 때) "오늘의 날" 목록을 계산해서 방에 알려요(`MemorialTodayState`). 시각은 늘 **서버의 한국 시간(Asia/Seoul)** 이에요. 기기 시계를 믿지 않아요.
- 칸 장식(3D, 칸 안 소품 인스턴스에 더해요):
  - 생일: 작은 생크림 케이크(초 1개), 파스텔 가랜드, 풍선은 쓰지 않아요(추모관 분위기).
  - 기일·49일·100일: 흰 국화 화환이 칸 앞턱에, 크림색 리본에 "1주기"·"49일"·"100일". 칸 줄조명이 조금 더 따뜻해져요.
  - 가까이 보기 카드 위에 한 줄 띠: "오늘은 콩이의 무지개다리 1주기예요"(시안 ①).
- 홀 안내:
  - 이름 찾기 키오스크와 안내원 대화에 **"오늘 기억하는 아이들"** 줄이 생겨요(공개를 켠 칸만, 사진·이름·[가까이 보기]).
  - 들어올 때 안내원 인사에 한 마디가 더해져요: "오늘은 세 아이의 기억하는 날이에요."

### F2. 방문객 꽃 놓기 + 방명록

**꽃 놓기**
1. 헌화 꽃대(입구 동쪽)나 칸 카드의 [꽃 놓기]를 눌러요. 처음이면 꽃 3가지 중 고르기: 흰 국화, 안개꽃 다발, 노란 프리지어(모두 무료).
   - 꽃대에서 집으면 아바타가 손에 들고 다니다가 칸에서 [꽃 놓기]. 카드에서 바로 눌러도 돼요(윗칸도 똑같이 쉽게, 1차 결정).
2. 칸 앞턱에 꽃다발이 놓여요(바스락 소리). 방 안 모두에게 보이고, "하늘색토끼님이 꽃을 놓았어요"가 그 칸을 보는 사람에게만 작게 떠요.
3. 꽃은 **24시간** 보이고, 한 칸에 최대 5다발(오래된 것부터 사라짐). 누적 수 "꽃 128"은 영원히 남아요.
- 규칙: 한 사람(기기)이 같은 칸에 하루 1번, 하루 전체 20번까지. 서버가 홀 안에 있는지 검사해요(촛불과 같은 방식, `CANDLE_REACH_M`). 공유 페이지(F6)에서 놓는 꽃도 같은 규칙이고, 3D 칸에 그대로 보여요.
- 촛불(이미 있음, 1시간)과 꽃은 따로 세요.

**방명록 (가족에게 남기는 한 줄)**
- 1차 설계의 "편지"(아이에게 쓰는 200자, 가족만 보기 가능)와 구분해요. 방명록은 **찾아온 사람이 가족에게 남기는 공개 한 줄**이에요.
1. 칸 카드 [방명록 쓰기] → 한 줄 입력(최대 80자, 남은 글자 표시) → 이름은 내 마을 닉네임.
2. 보내기 전 한 번 보여 줘요: "가족이 읽게 돼요. 따뜻한 말로 남겨 주세요."
3. 서버가 검사(5-2) → 통과하면 바로 [방명록] 탭 맨 위에. 걸리면 "고운 말로 다시 써 볼까요?"(지금 채팅 문구를 그대로 써요). 걸린 글은 저장하지 않아요.
- 가족은 각 줄에 [숨기기], 그 사람 [이 칸에서 막기]가 있어요. 칸 전체 [방명록 닫기]도 있어요.
- 데스크의 "추모관 방명록"(1차 설계 12번 나가기)도 같은 장치로 만들어요. 대상만 칸 대신 `hall`이에요.

## 3. 서버가 정하는 것 (권한)

- 모든 "남는 것"은 서버가 받고 검사하고 저장해요. 클라이언트는 보여 주기만 해요.
- 시각은 서버 시계(한국 시간). 오늘의 날, 추모식 단계, 꽃 24시간, 촛불 1시간 모두.
- 위치 검사: 홀 안 꽃·촛불 = 지금 `candleCubby` 규칙(홀 안 + 거리), 정원 꽃·명패 = 정원 영역 안, 공유 페이지 꽃 = 위치 검사 대신 더 엄한 횟수 제한(5-2).
- 주인 검사: 칸을 고치는 모든 요청은 `Authorization: Device <기기 키>` → 서버가 SHA-256 해시로 `owner_key`를 찾아 그 `owner`가 claim의 주인인지 확인. 기기 키 원문은 저장하지 않아요.
- Colyseus 방 메시지(실시간, 홀·정원 안)와 HTTPS API(글·사진·설정)로 나눠요. 사진과 긴 글은 방으로 보내지 않아요.

## 4. 데이터와 저장

### 4-1. 누가 주인인가 — 지금(기기) / 나중(계정)

```
owner (주인)          ← 칸·사진·권리·지갑(나중)이 모두 여기에 붙어요
  ├─ owner_key: device   (지금) 브라우저에 만든 무작위 32바이트 키. 서버는 해시만
  ├─ owner_key: device   (가족 초대로 붙인 다른 기기)
  ├─ owner_key: recovery (복구 코드 12자 — 기기를 잃었을 때)
  └─ owner_key: account  (나중) google:… / kakao:… / naver:…
```
- **지금(로그인 없음):** 첫 모시기 때 `owner`를 만들고 그 기기 키를 붙여요. 기기 키는 localStorage + IndexedDB 두 곳에 둬요(한쪽이 지워져도 남게). 복구 코드 12자를 "꼭 적어 두세요" 화면으로 보여 줘요(1차 설계는 6자리였는데, 추측을 막기 위해 12자로 늘려요).
- **가족 여러 명:** 초대 링크로 다른 기기 키를 같은 `owner`에 붙여요. 한 주인에 기기 최대 6개.
- **나중(로그인 생김):** 로그인하면 "이 기기의 추모 칸을 내 계정으로 옮길까요?" → `owner_key(kind=account)`를 **같은 owner에 하나 더 붙일 뿐**이에요. 칸·사진·권리·공유 링크 데이터는 움직이지 않아요.
  - 계정에 이미 다른 owner가 있으면(다른 기기에서 먼저 로그인) 두 owner를 하나로 합쳐요: 칸·권리·사진의 `owner_id`를 바꾸고, 옛 owner는 `merged_into`로 남겨요(되돌릴 수 있게).
  - 로그인 뒤에도 기기 키는 계속 쓸 수 있어요(로그인 안 한 가족 기기).
- 집(A8)·낚시 지갑도 나중에 같은 `owner`를 쓰면 마을 전체가 주인 하나로 이어져요. 그래서 이 표는 `memorial_` 접두어 없이 공용 이름으로 만들어요.

### 4-2. 표 (SQLite WAL, B단계 표에 더함)

B단계 표(1차 설계 Appendix): `slot`, `owner`, `claim`, `photo`, `decor`, `tribute`, `order`, `entitlement`. 아래는 바꾸거나 더하는 것이에요.

| 표 | 바꾸기·더하기 | 핵심 칸 |
|---|---|---|
| `owner` | 바꿈 | `id, nickname, created_at, merged_into NULL` (기기 해시는 `owner_key`로 옮김) |
| `owner_key` | 새로 | `id, owner_id, kind{device,recovery,account}, key_hash, provider NULL, label, created_at, last_seen_at, revoked_at` |
| `invite` | 새로 | `code_hash, owner_id, expires_at, used_at, used_by_key` |
| `claim` | 칸 더함 | `born, born_prec{day,md,unknown}, passed, passed_prec, days_json`(켠 날·공개 여부), `ceremony_optin{off,anniv_week,this_week}`, `guestbook_mode{open,closed}`, `album_visibility{public,family}` |
| `photo` | 칸 더함 | `album_order, caption(40), taken_on NULL, is_cover, visibility, deleted_at`, `moderation{pending,approved,rejected}`(있음) |
| `tribute` | 칸 더함 | `target{slot,garden,hall}`, `kind{flower,candle,letter}`, `sku`, `by_key_hash`, `expires_at` |
| `claim_stats` | 새로 | `claim_id, flowers, candles, guestbook` (누적 수, 화면은 이것만 읽음) |
| `guestbook` | 새로 | `id, target{slot,hall}, target_id, by_owner_id NULL, by_key_hash, nickname, text(80), status{visible,hidden_owner,hidden_reports,removed_admin}, ip_hash, created_at` |
| `report` | 새로 | `id, kind{guestbook,photo,claim}, target_id, by_key_hash, reason, created_at, resolved_at` |
| `block` | 새로 | `claim_id, key_hash, created_at` |
| `share_link` | 새로 | `code PK, claim_id, preview_photo BOOL, created_at, revoked_at` |
| `ceremony` | 새로 | `id, starts_at, participants, names_json, created_at` |
| `garden_spot` | 새로 | `id`(`G1-T01..T12`, 고정), `kind{tree,bench_plaque}`, `claim_id NULL`, `entitlement_id NULL`, `plaque_text` |
| `catalog` | 새로 | `sku PK, kind{decor,album_ext,frame,garden_tree,bench_plaque,flower,occasion_theme}, title, art_id, active` |
| `price` | 새로 | `sku, currency{FREE,KRW,COIN}, amount, term{once,year}, valid_from, valid_to` — 지금은 FREE 줄만 넣어요 |
| `entitlement` | B단계 것 넓힘 | `id, owner_id, claim_id NULL, sku, source{free,beta,krw,coin,grant}, order_id NULL, starts_at, ends_at NULL` |

- 칸 꾸미기·앨범 칸 수·기억 나무·디지털 액자·특별 장식은 **모두 `entitlement`를 읽어서** 보여 줘요. 화면 코드는 "돈인지 게임 돈인지" 몰라요. 그래서 나중에 상점·지갑이 생겨도 화면은 그대로예요.
- 게임 돈(COIN)은 지금 만들지 않아요. 나중에 `wallet(owner_id, balance)`와 `ledger(owner_id, delta, reason, ref)`를 더하고, 상점은 `price(currency=COIN)` 줄을 읽어 `entitlement(source=coin)`을 만드는 한 함수만 있으면 돼요.
- 방명록·꽃·촛불은 `owner`가 없어도(처음 온 방문객) 기기 키 해시로 남겨요. 그 사람이 나중에 주인이 되거나 로그인하면 `by_owner_id`를 채워요.

### 4-3. 사진과 앨범 저장

- **어디에:** Oracle 서버 디스크, git 체크아웃 밖 `/var/lib/caysonverse/media/` (B단계와 같은 곳). 매일 밤 SQLite와 함께 백업(같은 VM의 다른 디스크가 아니라 Object Storage로). Object Storage의 무료 용량은 계약 화면에서 확인한 뒤 정해요(확인 전 숫자는 쓰지 않아요).
- **올릴 때(기기):** `<input type="file" accept="image/*" multiple>`. iPhone은 사진 보관함에서 고르면 HEIC를 JPEG로 바꿔 줘요. 브라우저에서 긴 변 1600px로 줄이고 JPEG 0.85로 만들어 올려요. 원본 크기 제한 20 MB(줄이기 전), 올리는 파일 제한 2 MB.
- **서버에서:** 다시 디코드·인코드(이미지 처리 라이브러리, B단계에서 정한 것을 같이 씀). EXIF(위치 정보 포함)를 모두 지워요. 세 크기로 저장: 1600(크게 보기), 512(가까이 보기), 128(칸 아틀라스). WebP. SHA-256으로 같은 사진 두 번 올리기 막기.
- **크기 예산:** 사진 1장 ≈ 1600 280 KB + 512 45 KB + 128 6 KB ≈ 0.33 MB. 무료 5장 ≈ 1.7 MB/칸, 유료 30장 ≈ 10 MB/칸. 368칸이 모두 무료로 차면 ≈ 0.6 GB, 모두 30장이면 ≈ 3.7 GB. 디스크 70% 넘으면 운영자에게 알림(서버 로그 + 관리 화면 빨간 줄).
- **주소와 공개:**
  - 공개 승인된 사진: `/media/p/<무작위 22자>_<크기>.webp` (추측 불가, 오래 캐시).
  - 검토 중·가족만: `/media/s/<pid>_<크기>.webp?exp=…&sig=…` (서버 HMAC 서명, 10분짜리, 가족 기기 요청에만 발급).
  - 지운 사진: 30일 휴지통 뒤 파일까지 지움. 칸을 그만 모시면(B단계 `expired`) 사진은 90일 뒤 지움, 그 전에 가족이 [모두 내려받기](zip) 가능.
- **개인 정보:** 사진·이름·날짜 외에 아무것도 받지 않아요(이메일·전화 없음). IP는 횟수 제한용 해시(매일 바뀌는 소금)로만, 30일 뒤 지움. 이 내용을 모시기 화면에 한 줄로 알려요.

## 5. 지키기 — 나쁜 사용 막기

### 5-1. 가족이 할 수 있는 것
- 방명록: 줄마다 숨기기, 그 사람(기기) 이 칸에서 막기, 방명록 전체 닫기.
- 꽃: 원치 않는 꽃 치우기(그 꽃만 숨김, 누적 수는 그대로).
- 장식·앨범·공유 링크·추모식 이름: 각각 끄기.
- 가족 기기 목록: 이름(예: "엄마 폰"), 마지막 접속, [이 기기 빼기].

### 5-2. 서버 검사와 횟수 제한

| 대상 | 검사 | 횟수 (기기 키 해시 기준, IP 해시는 보조) |
|---|---|---|
| 방명록 | 지금 `profanity.ts`(서버 전용) + 링크·전화번호·카톡 아이디·계좌 모양 막기(`http`, `www.`, `.com`, 숫자 9자리 이상, `@`, "오픈채팅" 등) + 같은 글자 6번 넘게 반복 막기 + 80자 + 제어 문자 제거(`stripControl`) | 같은 칸 하루 1줄, 하루 전체 10줄, IP 하루 30줄. 기기를 처음 만든 지 10분 안에는 못 씀 |
| 꽃 | sku가 무료 목록에 있는지, 위치(홀·정원) | 같은 대상 하루 1번, 하루 20번 / 공유 페이지는 IP 하루 10번 |
| 촛불 | 지금 규칙 그대로(5초에 1번, 켜져 있으면 못 켬) | 같음 |
| 사진 | 파일 종류(매직 바이트), 크기, 해상도 64~8000px, 같은 사진 | 가족 하루 30장 |
| 신고 | 같은 사람 같은 대상 1번 | 하루 20번 |
| 공유 코드 조회 | 없는 코드를 연달아 묻기 | IP 1분 30번, 넘으면 10분 막기(코드 훑기 막기) |
| 추모식 촛불 | 추모식 "촛불 켜기" 단계일 때만, 한 사람 1번 | — |

- 신고 3건(서로 다른 기기)이면 그 방명록 줄·사진은 바로 숨기고 운영자 검토 줄에 올라가요. 가족이 남긴 신고는 1건으로도 숨겨요.
- 걸린 글은 저장·로그하지 않아요(지금 채팅 원칙). 운영자 화면에는 숨겨진 글만 보여요.
- 가족 칸 정보(이름·한 줄·사진 설명)도 같은 필터를 거쳐요(누군가 칸을 광고판으로 쓰지 못하게).

## 6. 유료가 될 자리 (조르지 않기)

**언제나 무료 (원칙)**
- 칸 모시기(베타), 대표 포함 사진 5장, 꽃 3종, 촛불, 방명록, 편지, 기억하고 싶은 날 기본 장식, 달력 알림, 공유 링크, 추모식, 정원 산책·벤치·기억의 돌에 꽃 놓기.

**유료 후보 (결제·게임 돈은 나중 단계, 지금은 `catalog`에 자리만)**

| sku 예 | 무엇 | 왜 괜찮은가 | 지금 |
|---|---|---|---|
| `album_ext_30` | 앨범 30장으로 늘리기 | 저장 비용이 실제로 듦 | catalog만, entitlement로 5장 제한 |

| `garden_tree_year` | 정원 기억 나무 한 그루 + 명패(1년) | 실제 수목장과 같은 개념, 12자리라 희소 | `garden_spot` + entitlement |
| `bench_plaque_year` | 정원 벤치 명패 "○○를 기억하며" | 실제 공원의 기념 벤치 | 같음 |

| `flower_premium_*` | (나중 검토) 방문객이 놓는 특별한 꽃 | 남의 칸에 돈 쓰기 → 압박이 될 수 있어 **출시 때 넣지 않기를 추천** | 없음 |

**보여 주는 규칙**
- 상품은 가족이 직접 여는 [꾸미기] 화면 맨 아래 "더 꾸미기"에만 있어요. 빨간 점, 남은 시간, "한정", 팝업, 할인 문구를 쓰지 않아요.
- 추모식·그날 띠·방명록·공유 페이지·방문객 화면에는 값이 절대 없어요.

- 나중에 게임 돈이 생기면 같은 상품을 COIN으로도 살 수 있게(price 줄 하나 더함). 슬픈 일로 게임 돈 버는 구조(촛불 켜면 동전)는 만들지 않아요.

## Appendix — technical notes (English)

**Dependency.** B14 assumes Stage B of memorial design 1 is live: SQLite (WAL) persistence, device-key owners, claim records, photo upload + moderation page, server-disk media store. Stage B builders should adopt §4-2's `owner`/`owner_key`/`entitlement`/`catalog`/`price` shapes up front.

**Clocks.** All occasion/ceremony logic uses server time in `Asia/Seoul`. Add `CV_FAKE_NOW` (ISO string or offset) honoured only when `NODE_ENV=test` or explicitly set in dev; never in `/etc/caysonverse.env`. Occasion rules: birthday on `born` month-day (Feb-29 → Feb-28 in non-leap years); anniversary on `passed` month-day for years ≥ 1 (`N주기`); d49 = passed + 48 days, d100 = passed + 99 days (day 1 = the day itself, Korean count), only if enabled.

**Ceremony scheduler.** Process-wide singleton like `CANDLES`: computes next Sunday 20:00 KST; phases `gather(-5m) → open(30s) → names(4s × n, cap 40) → light(60s) → silence(60s) → close(20s) → afterglow(60m)`. Broadcasts `CeremonyState{phase, phaseEndsAt, serverNow}` to every village room on phase change and to joiners; clients interpolate with `serverNow` offset. Participants = distinct sessions in any hall during `names..close`; lit count kept per ceremony id.

**Share codes.** 40 random bits → 8 Crockford base32 chars (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, input normalised: uppercase, strip `-`, map O→0, I/L→1). One active code per claim; revoke sets `revoked_at`. `GET /share/m/:code` returns HTML with `og:title`, `og:description`, `og:image` (hall card or approved 1200×630 crop when `preview_photo`), `robots: noindex`. Vercel `rewrites: [{ "source": "/m/:code", "destination": "https://<server>/share/m/:code" }]`.

**Auth header.** `Authorization: Device <base64url 32B>`; server `sha256` → `owner_key.key_hash` (kind device|recovery). Invite: 12-char code, stored hashed, 24 h, single use, max 6 device keys per owner. Recovery code: 12 chars base32, hashed with a slow KDF (scrypt) since it is user-held.

**Account migration (later).** `linkAccount(ownerId, provider, subject)`: insert `owner_key(kind=account)`; if the account already maps to owner B ≠ A, `mergeOwners(A→B)` in one transaction: update `claim.owner_id`, `photo` (via claim), `entitlement.owner_id`, `owner_key.owner_id`, set `A.merged_into = B`. Share codes are keyed by `claim_id`, so they survive. Unit test required (§9 #30).

**Economy hook (later, not built).** `wallet(owner_id PK, coin)`, `ledger(id, owner_id, delta, reason{fish_sale,purchase,grant,refund}, ref, created_at)`; `purchase(ownerId, sku, currency)` = read `price` → debit ledger (COIN) or order (KRW) → insert `entitlement(source=coin|krw)`. Rendering reads entitlements only. No coin rewards for memorial actions.

**Moderation filter additions** (server only, next to `profanity.ts`): URL/domain regex, phone (`0\d{1,2}[- .]?\d{3,4}[- .]?\d{4}`), 9+ digit runs, `@handle`, `오픈채팅|카톡|텔레|라인 ?아이디`, 6+ repeated chars; same NFC/fold pipeline; reject never logs text.

**Garden geometry** (village coords, see `plan_garden.py` for exact polylines): path loop ≈ 115 m, width 1.5 m; stream z ≈ −80, x −26..27, width 2.6 m, pond at (−21, −79); bridge x −1.1..1.1, z −82.9..−77.1, arch rise 0.6 m; memorial stone (0, −91.8); 12 tree spots `G1-T01..T12`; 4 backless benches; 13 bollards. Must be validated against village colliders, terrain and the far-mountain backdrop before modelling; grow `villageLayout` with a `memorialGarden` block and colliders generated from Blender `col__garden_*` like the hall.
