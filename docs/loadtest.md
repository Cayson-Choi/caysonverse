## 1. 어떻게 실행하나

```bash
# 1) 프로덕션 번들 빌드 + 서버 기동 (tsx 오버헤드가 측정을 오염시키지 않도록 번들 실행)
npm run build
NODE_ENV=production node server/dist/index.cjs   # PORT 기본 2567, ADMIN_CODE는 설정하지 않음

# 2) (다른 터미널) 서버 리소스 측정 — 서버 PID는 작업관리자나
#    Get-NetTCPConnection -LocalPort 2567 -State Listen 으로 확인
node loadtest/measure.mjs --pid <서버PID> --duration 660 --interval 5 --out measure.csv

# 3) (다른 터미널) 100봇 실행 — 630초 (기본 4프로세스 샤딩, 아래 3절 참고)
npm run loadtest -- --numClients 100 --duration 630 --endpoint http://localhost:2567
```

- `npm run loadtest`는 `loadtest/run.mjs`(샤드 런처)로 인자를 그대로 넘긴다(pass-through).
  옵션: `--numClients`(기본 100), `--shards`(기본 4), `--duration`(초, 기본 600), `--endpoint`, `--statusDir`,
  `--zone lounge|lectureHall`(2026-10-31 추가 — 봇의 걷기 목표를 그 방 안에서만 뽑는다. 교실 100명 장면용, 6장 참고).
- 봇 스크립트를 소규모로 직접 돌릴 때는: `npm run bot -w loadtest -- --room world --numClients 10 --endpoint http://localhost:2567`
  (@colyseus/loadtest `cli(main)` 패턴 — `--room world`가 필수다.)
- 봇 행동: 10Hz 합법 이동(공유 `resolveCollision`으로 장애물 슬라이드, 매 틱 서버 권위 위치에 재고정),
  봇의 20%는 8~15초마다 채팅 1건, 30%는 5~10초마다 이모지 1건 — 전부 서버 rate limit 안쪽이다.
- 조작 개편(2026-10-31) 이후 봇 행동 추가: 새 목표를 뽑을 때마다 30% 확률로 그 구간을 달리기 속도(`RUN_SPEED`)로 걷고,
  봇의 20%는 4~10초마다 점프 1건, 채팅하는 봇(20%)은 채팅 1.5~3초 전에 "입력 중" 켜기, 채팅 직후 끄기를 보낸다.
  점프·채팅 봇은 봇 번호로 고르게 뽑는다(10봇 스모크도 항상 점프 2명·채팅 2명). 통계에 `jumpsSent`·`typingSent`(켜기+끄기)·`runMovesSent`가 더해졌다.

## 3. 진단 여정 — 부하 생성기 쪽 함정 2가지 (서버는 내내 멀쩡했다)

@colyseus/loadtest는 한 프로세스 안에 numClients개의 연결을 만든다. 첫 시도들에서 봇이
집단 절단되거나 이동이 멎는 현상이 나왔는데, 진단 결과 **모두 서버가 아니라 부하 생성기
쪽** 문제였다 (문제 시점 서버 CPU ~2.5%):

**(1) @colyseus/loadtest TUI의 O(n²) 로그 누적 → 집단 절단.** 봇이 `room.onMessage`를
등록하지 않으면 SDK가 수신 브로드캐스트(채팅·이모지)마다 `console.warn`을 호출하는데,
loadtest의 `cli()`는 console.warn을 가로채 **계속 자라는 TUI 로그 문자열에 앞붙이기 +
전체 화면 재렌더**를 한다. 시간·클라이언트 수에 대해 O(n²)로 비대해져 이벤트 루프를
질식시키고, WS pong이 서버 ping 정책(3초 × 2회 ≈ 6초)을 놓쳐 **프로세스의 전체 봇이
한꺼번에 1006으로 강제 종료**된다 (100봇 단일 프로세스: 조인 완료 약 6초 만에 전멸;
25봇×4: 순단 248/재접속 216 폭풍; 10봇×10: 약 2분부터 서서히 붕괴). 수정: bot.ts가
와일드카드 핸들러 `room.onMessage("*", ...)`를 등록 — 실제 클라이언트도 어차피 구독한다.
수정 후에는 **단일 프로세스 100봇도 코어의 ~8%로 안정** 동작한다.

**(2) 직선 랜덤워크는 이 맵에서 랜덤워크가 아니다 → 이동 정지.** 목표가 칸막이벽 반대편에
있으면 봇이 벽을 따라 미끄러지다 z가 목표와 같아지는 순간 벽을 미는 상태로 **영원히
정지**한다(도착 판정 불가 → 새 목표도 안 뽑음). 수 분 안에 100봇 대부분이 x=±0.65(칸막이
면)에 얼어붙어 패치 트래픽이 클라이언트당 ~0.4KB/s로 붕괴한 것을 관찰자 프로브로 확인했다.
수정: bot.ts가 칸막이 반대편 목표는 **문(z∈±2) 경유 웨이포인트**로 라우팅하고, 30틱 동안
0.05m 미만 이동 시 목표를 다시 뽑는 안전망을 둔다.

`run.mjs`는 봇을 여러 OS 프로세스로 나누고(기본 4샤드 — 수정 후 필수는 아니고 안전 마진)
닉네임 오프셋(CV_BOT_OFFSET)을 부여한다 — 같은 머신에서 도는 로컬 실행이며 분산 부하
생성이 아니다. 실제 서비스의 브라우저 클라이언트 1명은 자기 연결 1개만 디코딩하므로
이런 생성기 함정과 무관하다.

## 5. 판정과 주의사항

- **판정: 통과 (로컬 기준).** 100봇 × 10분 이상, 절단·오류 0으로 세 게이트 모두 큰 여유로 통과.
- **로컬 ≠ Railway.** 이 수치는 Ryzen 7 6800H 데스크톱급 코어 기준이다. Railway 1 vCPU는
  이보다 느릴 수 있으므로 여유 배율을 그대로 믿으면 안 된다. 다만 측정된 마진(p95 CPU 기준
  약 4배)이 커서, 30분 게이트(사전 런칭 게이트)도 Railway에서 통과할 가능성이 높다.
- 30분 게이트는 이 태스크의 범위가 아니다(브리프: 로컬 10분이 이번 증거). 배포(Task 13) 후
  동일 스크립트로 30분 실측할 것.
- 서버와 봇이 같은 머신이라 네트워크 지연·패킷 손실이 0이다. 실환경에서는 재접속 로직이
  더 자주 개입할 수 있다.
- 봇 10Hz 틱은 setInterval 지연으로 실효 ~9.2Hz다. 이동 스텝은 틱 간격이 아니라 스텝
  길이 기준으로 합법이므로 서버 검증과는 무관하다.
- ADMIN_CODE 미설정 상태로 실행 — 관리자 경로(공지/강퇴)는 부하 시나리오에 포함되지 않는다
  (실사용에서도 관리자는 1명이라 부하 기여가 무시할 수준).

### 6.1 무엇이 달라졌나 (봇 행동 · 도구)

실사용 비율을 봇에 넣었다(`loadtest/bot.ts`, 1절 마지막 항목 참고).

| 행동 | 비율 | 서버 제한 |
|---|---|---|
| 달리기 | 새 목표를 뽑을 때마다 30%가 그 구간을 `RUN_SPEED`(6.4 m/s)로 이동 | 이동 예산 `RUN_SPEED` × 경과시간 × 1.5 |
| 점프 | 봇의 20%가 4~10초마다 1건 | 0.8초에 1번 (봇 간격이 5배 이상 느림) |
| 입력 중 | 채팅하는 봇(20%)이 채팅 1.5~3초 전에 켜기, 채팅 직후 끄기 | 켜기 3초에 1번 |

- `--zone lectureHall`(`CV_BOT_ZONE`): 봇의 걷기 목표를 강의실 안에서만 뽑는다(교실 100명 장면). 입장은 로비라서 첫 20~30초 동안 문을 지나 강의실로 모인다.
- 10봇 스모크(`npm run bot -w loadtest -- --room world --numClients 10`): 160초 동안 절단·순단·오류 0, 점프 45건, 입력 중 54건(켜기 27 + 끄기 27), 이동 15,108건 중 달리기 4,002건(26%). 점프·채팅 봇은 봇 번호로 고르게 뽑아 10봇에서도 항상 2명씩 나온다.
- 확인 프로브(관찰자 클라이언트가 봇 100명의 서버 위치를 1초 간격으로 40초 읽음, 옛 봇 vs 새 봇): 평균 속도 1.58 vs 1.60 m/s, 거의 안 움직인 표본(초당 0.3 m 미만) 29% vs 34%, 최고 속도 4.0 vs **6.4 m/s**. 달리기 이동이 서버에서 그대로 받아들여지고 전체 이동 모양은 옛 봇과 같다.

### 6.3.1 이름표 비용 고치기 (2026-11-01, 조작 개편 Task 14 보완)

같은 장면·같은 스크립트·같은 PC(봇 100명 `--zone lectureHall`, 375×812, CPU 4배, 20초 샘플)에서 **먼저 프로파일**(CDP 샘플링 프로파일러 + 프레임 단계별 임시 타이머)로 시간이 어디 가는지 쟀고, 원인을 고친 뒤 세 번 다시 쟀다. 임시 계측은 되돌렸고 커밋하지 않았다.

**프로파일로 알게 된 것** (고치기 전, 4배, "가까운 사람만", 20초 ≈ 280프레임)

1. 프레임 평균 1.04~1.29 ms = 머리 위치 계산 0.29 + 5 Hz 선택 0.09(한 번에 약 0.3 ms) + 벽 가림 광선 0.02 + 이름표별 갱신 0.64~0.85. 광선은 8개/프레임이어도 한 개에 약 2 µs라 사실상 공짜다.
2. "끄기"의 바닥값 0.7 ms는 보여 줄 것이 없는데도 등록된 104개 전부의 월드 위치(`getWorldPosition` — 부모까지 행렬을 다시 계산)·투명도·크기·올림·말풍선 높이를 매 프레임 계산한 값이다.
3. **Task 19의 "5 Hz 선택 패스가 프레임을 +1.5~2.5 ms 키운다"는 추정은 틀렸다.** 선택 패스 자체는 약 0.3 ms(p95 0.4)다. 1.5 ms를 넘은 프레임 54개 중 51개가 `setTyping`/`setHighlight`에서 0.5 ms 이상을 썼다. 이름표 모양(입력 중 "…", 방금 말한 사람의 테두리)이 바뀔 때마다 새 캔버스를 그려 질감을 만드는데(20초에 86번, 한 번에 0.67 ms), 채팅 한 줄이 모양을 2~3번 바꾸고(입력 중 → 테두리 → 원래대로) 마지막 소유자가 놓으면 질감을 버려서 다음 채팅에서 또 그린다. 선택 패스와 같은 프레임에 몰린 까닭은, 그 패스에서 새로 뽑힌 이름표가 처음 보이는 순간 모양을 바꾸기 때문이다.

**고친 것** (보이는 동작은 그대로 — 아래 "같음 확인")

1. **잠든 이름표는 프레임마다 아무것도 안 한다** (`nametagFrame.ts`). 뽑히지 않았고, 투명도 0이고, 올림이 제자리이고, 주인의 말풍선도 없으면 "잠든" 이름표다. 모든 이름표의 머리 위치는 5 Hz 선택 프레임에만 갱신하고, 그 사이에는 깨어 있는 것(교실 100명에서 30개 안팎, "끄기"에서는 0개)만 갱신한다. 벽 가림 검사는 그대로 프레임당 8명 라운드로빈이고, 잠든 이름표도 검사 때 위치를 새로 구한다.
2. **머리 위치 계산이 싸졌다.** 부모의 월드 행렬을 프레임당 한 번만 갱신하고 이름표마다 `부모 월드 × 로컬 위치`(= `getWorldPosition`과 같은 값)만 곱한다. 행렬을 손으로 넣은 앵커는 three의 원래 경로를 쓴다.
3. **말풍선**: 이름표마다 `bubbleRegistry.get`(호출마다 만료 정리)을 부르던 것을 프레임당 한 번 `visibleInto`(`get`과 같은 가시 규칙)로 보이는 말풍선 목록을 받아 이름표에 나눠 준다. 말풍선만 있고 숨은 이름표는 말풍선 높이만 갱신하는 가벼운 길로 간다.
4. "끄기"에서는 선택 패스가 투영·정렬을 하지 않는다. 선택·쌓기에 쓰는 배열과 사각형은 재사용한다. 쌓기 올림은 제자리에서 0.1 mm 이내가 되면 0으로 맞추고 잠든다(지수 감쇠는 0에 닿지 않는다).
5. **모양 바꾸기는 선택 패스 프레임을 피한다.** 입력 중 "…"·테두리를 바꾸는 일(캔버스를 그릴 수 있는 일)이 5 Hz 선택과 한 프레임에 겹치지 않게 다음 프레임으로 한 프레임 미룬다. 두 프레임 연속으로는 미루지 않아서 5 fps 아래에서도 굶지 않는다.
6. **놓은 모양을 보관한다** (`nametag.ts`). 마지막 소유자가 놓으면 GPU 질감은 전과 같이 바로 `dispose`하지만 캔버스는 "놀고 있는 모양" 풀에 둔다(`NAMETAG_IDLE_LOOKS` = 96개, 오래된 것부터 버림, 약 9 MB 이하). 같은 모양이 다시 필요하면 새로 그리지 않고 꺼내 쓰고(three가 질감을 다시 올린다), 같은 이름으로 다시 들어온 학생도 쓴다.
7. 테스트: `nametagFrame.test.ts` 29 → 42개(잠든 이름표는 setter·말풍선 앵커를 안 건드림, "끄기"에서 0, 깨어남·다시 잠듦, 잠든 이름표가 움직이면 선택이 알아봄, 숨은 말하는 사람의 말풍선 높이, 올림이 정확히 0으로 돌아옴, 잠든 이름표도 벽 가림 검사, 부모·중첩 부모·손으로 넣은 행렬, 선택 프레임에서 모양 바꾸기 미룸·굶지 않음), `nametag.test.ts`(보관·재사용·96개 상한·GPU 해제 유지), `bubbleRegistry.test.ts`(`visibleInto`). 새 로직을 하나씩 망가뜨려 보면 각각 테스트가 실패하는 것도 확인했다.
